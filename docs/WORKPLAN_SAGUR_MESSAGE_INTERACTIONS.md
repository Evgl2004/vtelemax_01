# Рабочий документ: кнопки в сообщениях рассылки SAGUR -> vtelemax

Дата фиксации: 2026-08-20.

Последнее уточнение: 2026-08-20. Живые испытания рабочих Telegram-, ВК- и MAX-ботов подтвердили удаление `l/d` из уже доставленного текстового сообщения с сохранением кликабельной `m`. На всех трёх платформах два последовательных реальных нажатия одной `m` получили разные платформенные идентификаторы; в безопасном журнале это доказано разными SHA-256-отпечатками. В VK дополнительно выявлено выходное поле клавиатуры `author_id`, которое нельзя возвращать в `messages.edit`; после формирования клавиатуры по явному списку входных полей изменение прошло успешно. В MAX выявлен пустой низкоуровневый ответ `{}`, отклоняемый платформой; штатный `event.answer("")` сформировал непустой ответ и был принят. Утверждён составной ключ идемпотентности `platform + bot_scope + platform_callback_id`: повтор с тем же ключом не создаёт вторую строку. Техническая повторная доставка одного события с новым идентификатором не воспроизводилась и считается новым событием, поскольку неотличима от нового реального нажатия. SAGUR письменно утвердил версию 2 служебного JSON с составным `a`; версия 1 сохраняется для ранее доставленных сообщений. Завершённые события в первой реализации автоматически не удаляются и не архивируются. Ответ на обратный вызов кнопки и продвижение позиции длительного опроса являются разными операциями, но из этого не следует обязательная переделка опроса.

Статус документа: зафиксированный результат анализа документации SAGUR, текущего кода vtelemax и договорённостей с владельцем проекта. Реализация ещё не начиналась: таблица событий, обработчики кнопок, отправитель событий и миграции в vtelemax пока не созданы.

## 3. Рамки текущей задачи

В задачу входит обработка четырёх кнопок, которые SAGUR добавляет в сообщения рассылки:

| Код действия | Значение для пользователя |
|---|---|
| `l` | «Нравится» |
| `d` | «Не нравится» |
| `m` | «Главное меню» |
| `c` | «Купоны» |

В задачу входят:

1. получение нажатий в ботах Telegram, VK и MAX;
2. локальная надёжная фиксация каждого реального нажатия;
3. выполнение пользовательского действия в боте;
4. пакетная отправка событий нажатия в SAGUR;
5. защита от технических повторов одного и того же входящего события;
6. корректное взаимодействие с текущим режимом обращения в поддержку;
7. проверка на рабочих ботах с заранее выбранными телефонными номерами и учётными записями.

В текущую задачу не входит перевод ботов на веб-перехватчики (webhook). Сейчас все три бота получают события опросом (polling), и это ограничение сохраняется, пока владелец проекта явно не расширит рамки задачи.

## 4. Термины и идентификаторы

### 4.1. `interaction_id` — уникальный код сообщения со стороны SAGUR

`interaction_id` создаёт SAGUR.

Он обозначает **одно конкретное интерактивное сообщение рассылки, отправленное одному конкретному получателю**.

Все кнопки внутри этого сообщения содержат один и тот же `interaction_id`. Отличается только код действия.

Пример кнопок одного сообщения:

Для новых сообщений утверждена версия 2:

```json
{"t":"si","v":2,"i":123456,"a":"ldm"}
{"t":"si","v":2,"i":123456,"a":"dlm"}
{"t":"si","v":2,"i":123456,"a":"mld"}
```

Версия 1 `{"t":"si","v":1,"i":123456,"a":"l"}` продолжает приниматься для ранее доставленных сообщений.

Расшифровка:

| Поле | Значение |
|---|---|
| `t` | тип полезной нагрузки; для кнопок SAGUR равен `si` |
| `v` | версия формата: `1` для совместимости или утверждённая `2` |
| `i` | `interaction_id`, то есть код конкретного сообщения SAGUR |
| `a` | в версии 1 — действие `l`, `d`, `m` или `c`; в версии 2 — одно из `ldm`, `dlm`, `mld`, `ldc`, `dlc`, `cld`, где первый символ является действием |

Важно:

1. `interaction_id` не является кодом отдельного нажатия.
2. Повторное реальное нажатие кнопки того же сообщения сохраняет тот же `interaction_id`.
3. Другое сообщение SAGUR, даже тому же пользователю, должно получить другой `interaction_id`.
4. vtelemax не создаёт и не изменяет `interaction_id`, а только извлекает его из кнопки и передаёт обратно в SAGUR.

### 4.2. Код входящего события платформы

Когда пользователь нажимает кнопку, мессенджер формирует входящее событие обратного вызова. У этого события есть собственный технический идентификатор платформы:

| Платформа | Идентификатор входящего события |
|---|---|
| Telegram | `callback_query.id` |
| VK | `event_id` события обратного вызова |
| MAX | `callback.callback_id` |

Этот идентификатор находится не внутри JSON SAGUR, а в оболочке входящего события самого мессенджера.

Документация SAGUR предполагает использовать его для различения:

1. нового реального нажатия пользователя;
2. повторной технической доставки сведений об уже полученном нажатии.

Для первой версии платформенный идентификатор утверждён как доступный ключ защиты от технических повторов. Живые проверки новых реальных нажатий выполнены на всех трёх рабочих ботах; техническая повторная доставка одного события не воспроизводилась. Правило применяется с явно ограниченной гарантией:

1. каждое проверенное новое реальное нажатие получило новый идентификатор;
2. сочетание `platform + bot_scope + platform_callback_id` сохраняется в локальной строке и защищается уникальным ограничением базы;
3. вставка выполняется атомарно без предварительного просмотра истории; конфликт этого ключа не создаёт вторую строку и новый `event_id`;
4. неизвестно, сохраняется ли прежний идентификатор при технической повторной доставке;
5. если платформа при техническом повторе выдаст новый идентификатор, vtelemax не сможет достоверно отличить такой повтор от нового реального нажатия только по доступным данным.

Это решение защищает от повторного получения события с тем же платформенным идентификатором и при этом не объединяет проверенные новые реальные нажатия. Оно не является недоказанным обещанием распознать технический повтор, которому платформа присвоила новый идентификатор. При такой неопределённости сохраняется приоритет недопущения потери реального нажатия, поэтому новый платформенный идентификатор создаёт новую строку.

**Живые подтверждения:** в Telegram 19 августа 2026 года первое нажатие `l` и два последовательных нажатия сохранённой `m` дали три разных отпечатка `callback_query.id`; все исходные идентификаторы имели длину 19 цифр. В VK 20 августа 2026 года две реальные попытки `l` и два последовательных нажатия сохранённой `m` также дали разные отпечатки; идентификаторы имели длину 12 символов и не были десятичными. В MAX 20 августа 2026 года нажатие `l` и два последовательных нажатия сохранённой `m` дали три разных отпечатка `callback.callback_id`; идентификаторы имели длину 116 байт и не были десятичными. Следовательно, во всех трёх проверенных сценариях новые реальные нажатия различимы по платформенному идентификатору. Техническая повторная доставка не воспроизводилась ни на одной платформе.

### 4.3. `event_id` — уникальный код события vtelemax

`event_id` создаёт vtelemax при первой успешной локальной фиксации нового нажатия.

Для каждого нового реального нажатия создаётся новый `event_id`.

Если отправка в SAGUR не удалась и выполняется повторная попытка, `event_id` не меняется. Это позволяет SAGUR понять, что пришёл повтор уже известного события, а не новое нажатие пользователя.

### 4.4. `occurred_at` — время фиксации нажатия в vtelemax

Согласованное значение `occurred_at`:

> Серверное время, когда vtelemax впервые получил событие нажатия и смог успешно зафиксировать его в своём надёжном хранилище.

Это не время, выставленное телефоном пользователя, и не предполагаемое время физического касания экрана.

## 5. Главное правило хранения нажатий

> **Каждое новое реальное нажатие пользователя создаёт новую строку события в vtelemax, получает новый `event_id` и передаётся в SAGUR. Это относится ко всем действиям `l`, `d`, `m` и `c`, включая повторные нажатия.**

Это прямое требование документации SAGUR:

1. `MESSAGE_INTERACTION_DECISIONS_2026-08-17.md:332` — vtelemax сохраняет каждое нажатие немедленно в своей надёжной исходящей очереди;
2. `MESSAGE_INTERACTION_VTELEMAX_ROADMAP_2026-08-17.md:131` — каждый новый реальный обратный вызов сохраняется и передаётся в SAGUR, включая противоположную повторную оценку;
3. `MESSAGE_INTERACTION_CONTRACT_2026-08-17.md:257` — повторная оценка с новым `event_id` сохраняется с результатом `rating_already_recorded`;
4. `MESSAGE_INTERACTION_CONTRACT_2026-08-17.md:259` — каждое реальное нажатие `c` и `m` с новым `event_id` сохраняется и входит в общий счётчик.

### 5.1. Оценки `l` и `d`

Пример последовательности для сообщения с `interaction_id = 123456`:

| Действие пользователя | Действие vtelemax | Действие SAGUR | Влияние на основную оценку |
|---|---|---|---|
| первое нажатие `l` | новая строка и новый `event_id` | новая строка с результатом `accepted` | устанавливает первую оценку |
| второе нажатие `l` | ещё одна новая строка и новый `event_id` | ещё одна новая строка с результатом `rating_already_recorded` | первую оценку не меняет |
| последующее нажатие `d` | ещё одна новая строка и новый `event_id` | ещё одна новая строка с результатом `rating_already_recorded` | первую оценку не меняет |

Таким образом, правило первой оценки ограничивает только основной показатель отчёта. Оно не запрещает хранение повторных нажатий.

### 5.2. Переходы `m` и `c`

Каждое реальное нажатие `m` или `c`:

1. создаёт новую строку события в vtelemax;
2. получает новый `event_id`;
3. передаётся в SAGUR;
4. сохраняется в SAGUR;
5. отдельно входит в общий счётчик переходов.

### 5.3. Решение для технического повтора и его граница

Документы `MESSAGE_INTERACTION_VTELEMAX_ROADMAP_2026-08-17.md:123` и `MESSAGE_INTERACTION_CONTRACT_2026-08-17.md:255` требуют не превращать повторную техническую доставку одного нажатия в новое событие.

Одновременно SAGUR требует сохранять каждое новое реальное нажатие. Чтобы выполнить оба требования, vtelemax должен доказанно отличать:

1. повторную доставку сведений об одном нажатии;
2. второе реальное нажатие той же кнопки.

Живые испытания Telegram, VK и MAX подтвердили новые идентификаторы при двух повторных реальных нажатиях одной кнопки. Однако поведение при технической повторной доставке не проверено ни на одной платформе. Поэтому платформенный идентификатор доказан как признак различия проверенных новых нажатий и используется как практический ключ идемпотентной вставки, но не даёт гарантии устранения повтора, если платформа создаст для него новый идентификатор.

Нельзя утверждать следующие более сильные правила:

- «одинаковый платформенный идентификатор всегда означает технический повтор»;
- «каждое новое реальное нажатие всегда получает новый платформенный идентификатор»;
- «техническая повторная доставка обязательно сохранит первоначальный идентификатор».

Утверждённый алгоритм первой версии: атомарная вставка с уникальным ключом `platform + bot_scope + platform_callback_id`; одинаковый ключ не создаёт новую строку, новый ключ создаёт новую строку и новый `event_id`. Предварительный поиск по истории не выполняется. Точное имя таблицы и синтаксис вставки определяются в миграции. Ограничение решения документируется для SAGUR.

## 6. Кто вообще может получить сообщение рассылки

**Факт текущей системы и уточнение владельца проекта:** незарегистрированный пользователь не получает сообщение рассылки, потому что ещё не завершил регистрацию и не входит в получателей.

Следовательно, не требуется проектировать сценарий нажатия кнопок рассылки полностью незарегистрированным пользователем.

При этом зарегистрированный пользователь может начать диалог с поддержкой, а затем получить сообщение рассылки. Этот сценарий обязателен к корректной обработке.

## 7. Согласованное поведение кнопок

### 7.1. Кнопки `l` и `d`

После каждого реального нажатия:

1. сохранить отдельное событие;
2. не изменять состояние обращения в поддержку;
3. удалить из исходного сообщения только кнопки оценки `l` и `d`;
4. оставить навигационные кнопки `m` и `c`, если они присутствовали;
5. не открывать главное меню и не отправлять лишнее сообщение пользователю.

Несмотря на удаление кнопок оценки после обработки, контракт допускает любое количество нажатий. Повторные нажатия возможны до обновления клавиатуры, при задержке обработки, из старой копии сообщения или при иных платформенных сценариях. Каждое реально полученное новое нажатие всё равно необходимо сохранить.

### 7.2. Кнопка `m` — «Главное меню»

После каждого реального нажатия:

1. сохранить отдельное событие;
2. если пользователь находится в ожидании ввода текста для поддержки, отменить только это ожидание;
3. не удалять обращение и не очищать историю поддержки;
4. открыть существующее главное меню напрямую;
5. отправить меню новым сообщением;
6. не имитировать команду `/start`.

### 7.3. Кнопка `c` — «Купоны»

После каждого реального нажатия:

1. сохранить отдельное событие;
2. если пользователь находится в ожидании ввода текста для поддержки, отменить только это ожидание;
3. не удалять обращение и не очищать историю поддержки;
4. открыть общий раздел купонов;
5. отправить раздел новым сообщением;
6. не выбирать автоматически какой-либо конкретный купон.

### 7.4. Почему кнопки нельзя передавать в общий обработчик команд

Полезную нагрузку SAGUR необходимо перехватывать до текущей логики меню и поддержки.

Причины:

1. общий обработчик не понимает формат SAGUR;
2. команда «Купоны» во время ожидания вопроса поддержке может быть ошибочно сохранена как текст вопроса;
3. текущая обработка MAX может воспринять JSON как неизвестную команду, показать главное меню и изменить исходное сообщение рассылки;
4. `l` и `d` вообще не являются переходами по меню.

### 7.5. Утверждённый пункт 6: пользователь, находящийся в поддержке

**Статус:** окончательно утверждено владельцем проекта 19 августа 2026 года.

Поведение четырёх кнопок:

1. `l` — сохранить отдельное событие оценки; состояние поддержки не изменять;
2. `d` — сохранить отдельное событие оценки; состояние поддержки не изменять;
3. `m` — сохранить отдельное событие, отменить только ожидание очередного пользовательского текста или контекст ответа, не закрывать обращение и не удалять историю, открыть главное меню новым сообщением;
4. `c` — сохранить отдельное событие, отменить только ожидание очередного пользовательского текста или контекст ответа, не закрывать обращение и не удалять историю, открыть общий раздел купонов новым сообщением.

Для кода это две общие ветки поведения (`l/d` и `m/c`), но все четыре кнопки проверяются отдельно. Исходное сообщение рассылки не заменяется меню или купонами. Пункт не требует новой подсистемы поддержки; он требует перехвата полезной нагрузки SAGUR до общего обработчика и точечного изменения только состояния ожидания при `m/c`.

Техническая возможность удаления `l/d` из исходного сообщения относится к отдельной проверке раздела 13.7 и не считается утверждённой только вследствие утверждения данного пункта.

## 8. Как кнопки обрабатываются сейчас

### 8.1. Общая архитектура

Все три бота сейчас получают обновления длительным опросом:

| Платформа | Текущий способ получения событий |
|---|---|
| Telegram | `dispatcher.start_polling` |
| VK | `bot.run_forever` |
| MAX | `dispatcher.start_polling` |

Переход на веб-перехватчики (webhook) не является частью текущей задачи.

### 8.2. Telegram

Текущий маршрутизатор обрабатывает известные точные значения кнопок. JSON SAGUR вида:

```json
{"t":"si","v":1,"i":123456,"a":"l"}
```

не соответствует существующим обработчикам.

Текущее следствие:

1. событие SAGUR локально не сохраняется;
2. действие кнопки не выполняется;
3. ответ на обратный вызов может не быть отправлен, поэтому у пользователя может остаться индикатор ожидания.

### 8.3. VK

Текущий маршрутизатор пытается извлечь обычную команду из поля `cmd`. В JSON SAGUR поля `cmd` нет.

Текущее следствие:

1. событие SAGUR локально не сохраняется;
2. действие кнопки не выполняется;
3. платформа получает пустой технический ответ на обратный вызов.

### 8.4. MAX

Текущий обработчик отвечает на обратный вызов, после чего передаёт JSON как строку в общий адаптер команд.

Для зарегистрированного пользователя строка может быть воспринята как неизвестная команда. В результате бот способен открыть главное меню и отредактировать либо заменить исходное сообщение рассылки.

Текущее следствие:

1. событие SAGUR локально не сохраняется;
2. требуемое действие не выполняется по специальным правилам;
3. пользовательский интерфейс может измениться неправильно.

## 9. Ответ пользователю и надёжность при текущем опросе

Необходимо различать:

1. **ответ на обратный вызов кнопки** — отдельный исходящий запрос по идентификатору конкретного нажатия: `answerCallbackQuery` в Telegram, `messages.sendMessageEventAnswer` в VK и `POST /answers` в MAX;
2. **продвижение позиции опроса** — выбор следующего `offset`, `ts` или `marker`, который библиотека использует при следующем запросе входящих обновлений;
3. **локальную фиксацию события** — отдельную транзакцию PostgreSQL vtelemax;
4. **передачу события в SAGUR** — последующую пакетную операцию независимого отправителя.

Ответ на обратный вызов может убрать индикатор ожидания, показать уведомление или ошибку и в зависимости от платформы изменить сообщение. Он не управляет `offset`, `ts` или `marker`, не доказывает наличие строки в PostgreSQL и не подтверждает приём события системой SAGUR.

Продвижение позиции опроса, в свою очередь, не сообщает пользователю об успехе и не доказывает выполнение прикладного действия. Платформа может перестать возвращать прежнее обновление, хотя обработчик не сохранил его и не ответил пользователю.

Проверка библиотек показала:

1. Telegram может запускать обработчики отдельными задачами, а позиция опроса продвигается независимо от завершения конкретного обработчика;
2. VK обновляет свою позицию опроса до полной обработки выданной пачки и маршрутизирует события асинхронно;
3. MAX обновляет маркер опроса до завершения обработки полученных событий.

Следовательно:

1. стратегия «не отвечать на кнопку, и платформа обязательно пришлёт её повторно» для текущей архитектуры ненадёжна;
2. наличие ответа на кнопку не означает, что событие сохранено;
3. отсутствие ответа на кнопку не возвращает позицию опроса назад;
4. при недоступности PostgreSQL возможна ситуация, когда пользователь видит ошибку или зависший индикатор, а техническое событие уже не приходит повторно;
5. этот риск не доказывает необходимость переделки опроса: такая необходимость возникает только при отдельно установленном требовании автоматически восстанавливать нажатия, пришедшие во время недоступности локальной базы.

Отдельное логическое ограничение: показать ошибку средствами ответа на обратный вызов и одновременно «не отвечать на обратный вызов» невозможно. Для показа такой ошибки требуется как раз вызвать платформенный метод ответа. Обычное отдельное сообщение пользователю возможно, но оно также не влияет на позицию опроса.

## 10. Недоступность локальной PostgreSQL: установленное и неустановленное

### 10.1. Установленные факты

1. Реестр решений SAGUR требует сначала надёжно сохранить событие в локальной исходящей очереди vtelemax, а затем независимо отправлять его в SAGUR.
2. Это требование явно защищает от временной недоступности SAGUR после успешной локальной записи.
3. Оно само по себе не устанавливает отдельную гарантию сохранения события в момент недоступности самого PostgreSQL vtelemax.
4. Дорожная карта vtelemax предлагает вернуть временную ошибку, чтобы обратный вызов мог быть повторён, но текущий опрос не гарантирует такой повтор только из-за отсутствия ответа на кнопку.
5. При обычной успешной работе PostgreSQL существующий способ опроса не мешает принять, сохранить и обработать каждое полученное нажатие SAGUR.

### 10.2. Нормальная последовательность без переделки опроса

1. Получить и проверить служебный JSON SAGUR.
2. Попытаться создать долговечную строку события в PostgreSQL.
3. После успешной фиксации ответить на обратный вызов.
4. Выполнить пользовательское действие.
5. Независимо передать сохранённое событие в SAGUR пакетным отправителем.

Эта последовательность не требует самостоятельного управления `offset`, `ts` или `marker`. Она исключает ложное сообщение об успешной фиксации, но не обеспечивает автоматического восстановления первоначального нажатия при недоступности PostgreSQL.

### 10.3. Статус ранее предложенных вариантов A, B и C

Ранее были предложены:

1. вариант A — оставить текущий опрос и просить пользователя повторить нажатие после ошибки базы;
2. вариант B — самостоятельно управлять позициями опроса;
3. вариант C — добавить отдельный долговечный журнал перед PostgreSQL.

**Исправленный статус:** это не три утверждённых варианта и не обязательный вопрос владельцу проекта. Варианты B и C имеют смысл только при явно установленном требовании гарантированно восстанавливать нажатия, полученные во время недоступности PostgreSQL. Такого отдельного утверждённого требования в реестре решений сейчас не установлено. Поэтому нельзя навязывать переделку работающего опроса только на основании разделения двух видов подтверждения.

Если позднее команда SAGUR или владелец проекта явно установят гарантию сохранения во время аварии локальной базы, тогда варианты защиты необходимо заново сравнить по фактам, стоимости и платформенным ограничениям. До этого они не являются блокирующим выбором для текущего анализа.

### 10.4. Практическое решение для текущей задачи

**Статус: окончательно утверждено владельцем проекта 19 августа 2026 года.** Пункт о разделении ответа на кнопку и продвижения позиции опроса закрыт как техническое ограничение и не требует дальнейшего выбора вариантов.

Для текущей доработки принимается следующая граница реализации:

1. существующий длительный опрос Telegram, VK и MAX не изменяется;
2. отдельное управление `offset`, `ts` и `marker` не разрабатывается;
3. дополнительный локальный журнал перед PostgreSQL не создаётся;
4. обработчик SAGUR сначала проверяет полезную нагрузку и пытается сохранить событие в PostgreSQL;
5. только после успешной записи выполняются пользовательское действие и ответ на обратный вызов;
6. при ошибке PostgreSQL нельзя сообщать об успешной фиксации, выполнять действие или удалять кнопки оценки;
7. пользователю можно сообщить об ошибке и оставить клавиатуру для ручного повторного нажатия;
8. автоматическое восстановление первоначального нажатия, пришедшего во время недоступности PostgreSQL, текущая архитектура не гарантирует и в эту доработку не добавляет.

Следовательно, из пункта 4 не возникает отдельной архитектурной работы. Следующий этап анализа — не обсуждение вариантов A, B и C, а обязательная проверка на рабочих ботах:

1. фактической структуры входящего обратного вызова Telegram, VK и MAX;
2. поведения платформенного идентификатора при двух реальных нажатиях;
3. возможности технической повторной доставки;
4. возможности после `l` или `d` удалить только оценочные кнопки и сохранить правильную кнопку `m` или `c`.

### Зафиксированная граница

Веб-перехватчики (webhook) могут быть будущей точкой развития, но не выбираются автоматически и не входят в эту доработку.

## 11. Предлагаемое локальное хранение событий

Локальной таблицы нажатий в vtelemax сейчас нет. Архитектурное решение о количестве таблиц утверждено, но точная физическая схема ещё не реализована.

**Утверждено владельцем проекта 19 августа 2026 года:** для событий нажатия и их текущего состояния доставки используется одна таблица. Отдельная таблица очереди в первую версию не вводится. Рабочее название может быть изменено при реализации. Требования к качеству физической схемы и индексам приведены в разделе 11.4.

### 11.1. Идентификация события

Минимальные поля:

| Поле | Назначение |
|---|---|
| `id` | внутренний числовой ключ строки |
| `event_id` | уникальный код события, созданный vtelemax |
| `platform` | `telegram`, `vk` или `max` |
| `bot_scope` | конкретный бот или сообщество внутри платформы |
| `platform_callback_id` | код входящего события, созданный мессенджером; входит в составной ключ защиты от повторной вставки |
| `interaction_id` | код интерактивного сообщения, созданный SAGUR |
| `action` | `l`, `d`, `m` или `c` |
| `occurred_at` | время первой успешной локальной фиксации |
| `provider_message_id` | код исходного сообщения в мессенджере, если доступен |

Ограничения:

1. `event_id` уникален;
2. сочетание `platform + bot_scope + platform_callback_id` уникально; повторная вставка того же ключа не создаёт новую строку и новый `event_id`;
3. `interaction_id` — положительное целое число достаточной разрядности;
4. `action` допускает только `l`, `d`, `m`, `c`.

Уникальность по `interaction_id + action` запрещена: она ошибочно уничтожит повторные реальные нажатия одной кнопки.

### 11.2. Состояние доставки в SAGUR

Нужны отдельные поля:

| Поле | Назначение |
|---|---|
| `delivery_status` | состояние доставки события в SAGUR |
| `delivery_attempts` | количество попыток |
| `next_attempt_at` | время следующей попытки |
| `delivery_locked_at` | время захвата строки отправителем |
| `sagur_result` | результат обработки элемента со стороны SAGUR |
| `sagur_acked_at` | время конечного подтверждения |
| код и текст ошибки доставки | диагностика последней ошибки |

### 11.3. Состояние пользовательского действия

Отдельно нужны:

| Поле | Назначение |
|---|---|
| `user_action_status` | выполнено ли изменение клавиатуры или открытие раздела |
| время завершения действия | когда действие закончилось |
| код и текст ошибки действия | диагностика ошибки интерфейса |

Состояние доставки в SAGUR и состояние пользовательского действия нельзя объединять. Возможны ситуации:

1. событие сохранено и отправлено в SAGUR, но клавиатуру изменить не удалось;
2. меню открыто пользователю, но SAGUR временно недоступен;
3. событие ожидает обе операции.

Если потребуется автоматически повторять пользовательское действие после перезапуска процесса, одного `provider_message_id` недостаточно. Например, в Telegram код сообщения уникален только внутри конкретного чата. Тогда потребуется безопасно сохранять также идентификатор чата или пользователя, необходимый конкретной платформе.

### 11.4. Профессиональная оценка варианта с одной таблицей

Одна таблица утверждена как архитектурный вариант первой версии. Это не отменяет обязательной проверки её физических индексов и производительности на прогнозном объёме.

Почему объединение допустимо:

1. бизнес-факт на стороне vtelemax — одно принятое нажатие;
2. для одного события в текущем контракте существует одна доставка в одного получателя — SAGUR;
3. состояние доставки связано с событием отношением один-к-одному;
4. событие и постановка в исходящую очередь создаются одной вставкой в одной транзакции;
5. отдельные таблицы события и очереди при текущих требованиях создали бы вторую строку на каждое нажатие и дополнительную связь; эта стоимость должна окупаться измеримой выгодой, но сам вариант не является плохим или непрофессиональным;
6. контракт не требует долговечно хранить каждую HTTP-попытку и каждый `request_id`: конкретная пакетная попытка трассируется безопасными структурированными журналами.

Следовательно, разделение одной связи один-к-одному только ради формальной нормализации не является улучшением. Модель соответствует упрощённому шаблону транзакционной исходящей очереди: сохранённый факт одновременно является готовой к отправке задачей.

Одна таблица перестаёт быть предпочтительным вариантом, если появляется хотя бы одно из требований:

1. обязательный долговечный аудит каждой HTTP-попытки — тогда нужна отдельная ограниченная по сроку хранения таблица попыток с отношением один-ко-многим;
2. существенно разные сроки хранения бизнес-событий и задач доставки;
3. несколько независимых получателей одного события;
4. независимая восстанавливаемая очередь пользовательских действий со своим расписанием, захватом и повторами;
5. измерения показывают, что большое число завершённых строк ухудшает выборку активной очереди и обслуживание таблицы;
6. локальная таблица становится источником отдельной долговременной аналитики с нагрузкой, конфликтующей с частыми обновлениями очереди.

Обязательные требования к качественной реализации одной таблицы:

1. поля факта (`event_id`, платформа, код обратного вызова, `interaction_id`, действие и `occurred_at`) после вставки не изменяются;
2. доставка в SAGUR и пользовательское действие имеют разные статусы, времена завершения, коды и тексты ошибок; одна общая ошибка для двух независимых операций недопустима;
3. захват строк выполняется короткой транзакцией через `FOR UPDATE SKIP LOCKED`, внешний HTTP-запрос не держит транзакцию базы открытой;
4. захват получает уникальный маркер аренды; поздний ответ старого работника не должен перезаписать результат нового работника после восстановления просроченного захвата;
5. выборка очереди использует частичный индекс только по активным состояниям, например по `next_attempt_at`, `created_at` и ключу строки при состояниях `pending/retry`; завершённые строки не должны раздувать горячий индекс очереди;
6. отдельный частичный индекс предусматривается для поиска просроченных строк в состоянии отправки по времени захвата;
7. уникальны `event_id` и составной ключ `platform + bot_scope + platform_callback_id`;
8. ограничения базы проверяют допустимые платформы, действия, статусы, положительный `interaction_id`, неотрицательное число попыток и согласованность обязательных времён со статусами;
9. полные HTTP-тела и список всех `request_id` не дублируются в строке события;
10. до выпуска оценивается ожидаемое число нажатий в сутки; с учётом утверждённого отсутствия автоматической очистки выборка очереди проверяется через `EXPLAIN ANALYZE` на прогнозном годовом объёме с запасом;
11. устанавливаются наблюдаемые показатели: глубина очереди, возраст старейшего ожидающего события, число повторов, просроченные захваты, заблокированные события и задержка подтверждения SAGUR;
12. в первой версии автоматическое удаление и архивирование завершённых строк не выполняются; данные хранятся бессрочно относительно текущего решения, пока отдельное эксплуатационное решение не установит иной порядок;
13. объём таблицы и горячих частичных индексов наблюдается. Если позднее появится политика очистки, она не должна разрушать защиту от технического повтора: строка либо компактный ключ-доказательство сохраняется не меньше подтверждённого окна повторной доставки платформы. Пока такое окно не доказано, безопасный срок удаления определить нельзя.

Архитектурный вывод:

- **для первой версии:** одна таблица утверждена владельцем проекта;
- **физическая оптимизация:** конкретные индексы и нагрузочные пределы ещё должны быть доказаны измерениями; решение первой версии об отсутствии автоматической очистки уже зафиксировано;
- **три таблицы заранее:** не оправданы текущим контрактом;
- **возможное разделение позднее:** выполняется только по новому требованию или результатам измерений, а не по абстрактному правилу «каждому состоянию своя таблица».

### 11.5. Критическая проверка варианта с отдельной таблицей очереди

Вариант с двумя таблицами технически корректен:

1. `message_interaction_events` хранит неизменяемый факт нажатия и ключи защиты от дублей;
2. `message_interaction_outbox` хранит изменяемое состояние доставки;
3. обе строки создаются в одной транзакции PostgreSQL;
4. после подтверждения SAGUR строка очереди удаляется либо недолго хранится завершённой.

Однако утверждение «отдельная очередь быстрее, потому что в ней мало строк» само по себе недостаточно. В одной таблице частичный индекс по состояниям `pending/retry` также содержит только активные задачи. При миллионе завершённых событий и двухстах ожидающих строк рабочий индекс одной таблицы может содержать те же две сотни строк. Поэтому предполагаемое ускорение выборки нельзя считать доказанным преимуществом второй таблицы.

Реальные потенциальные преимущества разделения уже и должны быть измерены:

1. изоляция частых обновлений, очистки мёртвых версий строк и обслуживания очереди от большой неизменяемой истории;
2. разные сроки хранения события и транспортной задачи;
3. независимая локальная аналитика по истории событий;
4. несколько независимых доставок одного события.

Цена разделения возникает всегда:

1. две вставки вместо одной на каждое нажатие;
2. дополнительная строка, внешний ключ и индексы;
3. соединение таблиц при отправке либо дублирование компактного содержимого события в очереди;
4. дополнительная логика завершения и очистки;
5. больше миграций, кода, конкурентных сценариев и тестов.

По текущим установленным требованиям:

1. получатель один — SAGUR;
2. доставка одного события одна;
3. отдельная локальная аналитика vtelemax не заявлена;
4. разные сроки хранения события и очереди не утверждены;
5. долговечная история каждой HTTP-попытки не требуется;
6. существующий механизм событий регистрации проекта уже использует одну объединённую строку.

Следовательно, сейчас вторая таблица не имеет доказанной выгоды, а её дополнительная стоимость гарантирована. **Текущая профессиональная рекомендация — одна таблица с частичными индексами активных состояний.** Двухтабличный вариант возвращается на рассмотрение только при новом требовании или измеренном узком месте: конфликте аналитики и очереди, разном сроке хранения, нескольких получателях либо подтверждённых проблемах обновления и очистки большой таблицы.

## 12. Рекомендуемая последовательность обработки одного нажатия

### 12.1. Общая последовательность

1. Получить входящее событие от Telegram, VK или MAX.
2. До общего меню и поддержки проверить, является ли полезная нагрузка кнопкой SAGUR.
3. Строго проверить JSON:
   - `t` равно `si`;
   - `v` равно `1`;
   - `i` является положительным целым числом;
   - `a` входит в `l`, `d`, `m`, `c`;
   - лишние или неоднозначные значения не выполнять как команды.
4. Извлечь код входящего события платформы и контекст исходного сообщения.
5. Создать новый `event_id` и выполнить одну атомарную вставку локальной строки события.
6. Защита от повторной вставки выполняется уникальным индексом по `platform + bot_scope + platform_callback_id` и атомарным `INSERT ... ON CONFLICT`, а не предварительным поиском всей таблицы.
7. Зафиксировать транзакцию PostgreSQL.
8. Только после успешной фиксации отправить технический ответ мессенджеру на нажатие.
9. Выполнить пользовательское действие `l`, `d`, `m` или `c`.
10. Отдельно сохранить результат пользовательского действия.
11. Независимый отправитель позже передаст событие в SAGUR.

### 12.2. Повтор одного технического события

Требуемое контрактом поведение: если доказано, что получена только повторная техническая доставка ранее сохранённого нажатия, новый `event_id` и новая строка не создаются.

Однако признак, по которому это можно доказать на каждой платформе, пока не подтверждён. Поэтому этот раздел описывает цель контракта, а не готовый алгоритм реализации.

До завершения платформенной проверки запрещено автоматически считать совпавший платформенный идентификатор достаточным доказательством технического повтора.

### 12.3. Новое реальное нажатие той же кнопки

Если доказано, что пользователь выполнил новое реальное нажатие:

1. создать новую строку;
2. создать новый `event_id`;
3. сохранить тот же `interaction_id`, если нажата кнопка того же сообщения;
4. повторно выполнить требуемое действие;
5. отправить отдельное событие в SAGUR.

### 12.4. Что означает «найти или создать» и почему полного поиска не будет

Прежняя формулировка «в одной транзакции найти или создать строку» не должна превращаться в последовательность `SELECT`, затем `INSERT` для каждого нажатия. Такой вариант создаёт лишнее чтение и гонку между одновременными обработчиками.

После того как на рабочих платформах будет подтверждён устойчивый ключ технического обратного вызова, нормальный путь нового нажатия выглядит так:

```sql
INSERT INTO message_interaction_events (...)
VALUES (...)
ON CONFLICT (platform, bot_scope, platform_callback_id) DO NOTHING
RETURNING event_id;
```

1. для нового реального нажатия PostgreSQL проверяет точный ключ в уникальном индексе и сразу вставляет строку;
2. отдельный предварительный `SELECT` не выполняется;
3. если вставка ничего не вернула, только тогда выполняется точечное чтение существующей строки по тому же уникальному индексу;
4. существующее событие сверяется по неизменяемым значимым полям; технический повтор не может изменить действие, `interaction_id` или время первоначальной фиксации;
5. искусственный `ON CONFLICT DO UPDATE` только ради возврата строки не рекомендуется: он создаёт ненужные версии строки и раздувает таблицу;
6. поиск по `interaction_id + action` не выполняется и уникальность по этим полям не вводится, потому что новые реальные повторные нажатия должны сохраняться отдельно.

Уникальный индекс выполняет адресную проверку ключа, а не линейный просмотр всех событий. Тем не менее это не даёт права обещать работу с миллиардом строк без измерений: при таком объёме становятся существенными размер индекса, память, накопитель, очистка мёртвых версий, резервное копирование и возможное секционирование таблицы. До реализации требуется прогноз объёма и нагрузочная проверка. В первой версии автоматической очистки нет; если она появится позднее, ключи защиты нельзя удалять раньше возможной технической повторной доставки платформы.

### 12.5. Обязательное требование: нажатие не должно зависать

**Утверждено владельцем проекта как требование качества:** размер накопленной истории и доступность SAGUR не должны приводить к заметному зависанию кнопки пользователя.

Синхронный путь одного нажатия должен содержать только:

1. извлечение и строгий разбор короткой полезной нагрузки;
2. одну атомарную индексированную вставку локального события;
3. фиксацию короткой транзакции PostgreSQL;
4. немедленный ответ мессенджеру, прекращающий состояние ожидания на кнопке.

В синхронный путь до ответа на кнопку запрещено включать:

1. обращение в SAGUR;
2. формирование и отправку накопленной пачки;
3. просмотр истории событий;
4. предварительный `SELECT` перед обычной вставкой;
5. ожидание фонового отправителя;
6. повторные попытки внешней доставки;
7. длительное удержание транзакции во время сетевого запроса.

Изменение клавиатуры, открытие меню или купонов выполняется после успешной локальной фиксации и технического ответа на кнопку. Результат пользовательского действия сохраняется отдельно от доставки в SAGUR. Если PostgreSQL недоступна или операция превысила ограниченное время ожидания, обработчик не изображает успешную фиксацию: он по возможности завершает платформенное ожидание сообщением об ошибке, оставляет кнопку доступной для повтора и записывает безопасную диагностику.

Должны быть ограничены время ожидания соединения из пула, время SQL-операции и время платформенного ответа. Конкретные числовые пределы утверждаются по базовым измерениям рабочей инфраструктуры до приёмки функции; отсутствие числовых критериев не допускается.

Наличие индекса не является достаточным доказательством быстродействия. Проверка проводится на реальном PostgreSQL с включённой долговечностью записи, таблицей прогнозного размера, конкурентными новыми нажатиями, техническими повторами и одновременно работающим отправителем.

## 13. Определение состава клавиатуры и возможное изменение JSON SAGUR

### 13.1. Что означает этот вопрос

Слово «сохранить» в этом разделе означает **оставить кнопку `m` или `c` видимой и доступной в исходном сообщении после удаления оценочных кнопок `l` и `d`**. Речь не идёт о сохранении букв `m` или `c` в таблице PostgreSQL.

SAGUR использует два набора кнопок:

```text
Набор «Оценка + меню»:
[ Нравится (l) ] [ Не нравится (d) ]
[             Меню (m)              ]

Набор «Оценка + купоны»:
[ Нравится (l) ] [ Не нравится (d) ]
[          В купоны (c)             ]
```

Полезная нагрузка нажатой оценки содержит только действие самой нажатой кнопки:

```json
{"t":"si","v":1,"i":123456,"a":"l"}
```

По этому JSON нельзя определить, находилась рядом кнопка `m` или `c`. Поле `i` определяет конкретное интерактивное сообщение, но не код набора кнопок. Отдельного локального справочника `interaction_id -> button_set` в vtelemax сейчас нет, а синхронно запрашивать SAGUR внутри пользовательского обработчика запрещено контрактом.

### 13.2. Технически возможная обработка текущей версии 1

В текущей версии 1 vtelemax не может определить навигационную кнопку по JSON нажатой оценки. Доступный для этой версии резервный алгоритм основан на фактической клавиатуре исходного сообщения:

1. получить всю текущую клавиатуру исходного сообщения;
2. разобрать полезную нагрузку каждой кнопки;
3. удалить только кнопки SAGUR, у которых `t="si"`, `v=1`, тот же `interaction_id` и действие `l` либо `d`;
4. все остальные кнопки, ряды, подписи и стили оставить без изменения;
5. передать отфильтрованную клавиатуру платформе как новую клавиатуру исходного сообщения.

Тогда результат определяется самой исходной клавиатурой:

```text
[[l, d], [m]] -> [[m]]
[[l, d], [c]] -> [[c]]
```

Обработчику не требуется знать имя набора `rating_menu` или `rating_coupons`. Он удаляет оценки из существующей структуры, поэтому правильная навигационная кнопка остаётся автоматически. Однако это переносит в vtelemax платформенную сложность получения и разбора клавиатуры только из-за отсутствия состава набора в служебном JSON. Поэтому данный алгоритм нельзя автоматически считать основным решением будущей реализации.

Точный статус изменения JSON:

1. утверждённая версия 1 сейчас содержит только поля `t`, `v`, `i`, `a`;
2. команда vtelemax не вправе самовольно добавить, например, поле набора кнопок и считать прежний контракт изменённым;
3. это не означает бессрочный запрет на пересмотр формата;
4. если проверка рабочих платформ докажет, что исходную клавиатуру невозможно получить или безопасно изменить, команда фиксирует воспроизводимый результат, после чего владелец проекта и команда SAGUR могут совместно утвердить новую версию JSON либо предварительный обмен сведениями о наборе;
5. до такого совместного решения текущий формат нельзя менять односторонне.

### 13.3. Критическая оценка цены текущего формата

Отсутствие признака набора уменьшает служебный JSON, но переносит сложность в vtelemax: для определения правильной навигационной кнопки приходится читать и разбирать фактическую клавиатуру отдельно на каждой платформе. Это решение нельзя считать оптимальным только потому, что формат версии 1 уже записан в документации.

Проверенный размер при максимальном положительном 64-битном `interaction_id`:

| Формат | Размер UTF-8 | Предел Telegram |
|---|---:|---:|
| текущая версия 1: `t,v,i,a` | 48 байт | помещается |
| версия 2 с составным трёхсимвольным `a` | 50 байт | помещается, остаётся 14 байт |
| версия 2 с отдельным `n:"m"` или `n:"c"` | 56 байт | помещается, остаётся 8 байт |
| пример с полным `s:"rating_menu"` | 66 байт | не помещается |

Следовательно, ограничение Telegram не мешает передать состав кнопок. Владелец проекта предложил более компактный вариант без отдельного поля: в версии 2 значение `a` содержит весь исходный набор, а первый символ обозначает фактически нажатую кнопку.

Предлагаемое правило:

1. первый символ `a` — фактически нажатая кнопка;
2. остальные символы — остальные кнопки исходного набора в их исходном порядке;
3. допускается только закрытый перечень значений, соответствующий двум фактическим наборам;
4. произвольные перестановки, повторяющиеся символы и неизвестные сочетания отклоняются.

Точная кодировка по фактическим наборам `l,d,m` и `l,d,c`:

| Исходный набор | Нажата кнопка | Значение `a` |
|---|---|---|
| `l,d,m` | `l` | `ldm` |
| `l,d,m` | `d` | `dlm` |
| `l,d,m` | `m` | `mld` |
| `l,d,c` | `l` | `ldc` |
| `l,d,c` | `d` | `dlc` |
| `l,d,c` | `c` | `cld` |

Пример нажатия положительной оценки в наборе с главным меню:

```json
{"t":"si","v":2,"i":123456,"a":"ldm"}
```

Из `a="ldm"` однозначно следует: нажата `l`, исходный набор содержал `l,d,m`, после оценки нужно удалить `l/d` и оставить `m`.

Потенциальные преимущества:

1. отдельное поле набора не требуется;
2. максимальный JSON увеличивается только на 2 байта относительно версии 1;
3. vtelemax не угадывает набор и не зависит от наличия полной клавиатуры только для определения `m/c`;
4. при фиксированных двух наборах можно сразу построить правильную оставшуюся кнопку;
5. уменьшается число платформенных ветвей и внешних запросов для восстановления состава клавиатуры;
6. исчезает причина добавлять локальный справочник `interaction_id -> button_set` или синхронно обращаться в SAGUR.

Ограничения этого улучшения:

1. поле `a` меняет смысл: в версии 1 это одно действие, в версии 2 — нажатая кнопка вместе с составом исходного набора;
2. поэтому изменение должно оформляться новой версией `v=2`, а не скрытым расширением версии 1;
3. платформенную операцию изменения сообщения всё равно необходимо реализовать и проверить;
4. в MAX и сообщениях с вложениями всё равно может потребоваться исходное сообщение, чтобы не потерять изображения и другие вложения;
5. уже отправленные сообщения версии 1 требуют совместимого обработчика: для них чтение исходной клавиатуры остаётся резервным путём;
6. версия 2 и закрытый перечень допустимых значений должны быть совместно утверждены SAGUR и vtelemax.

**Предложение команды vtelemax для письменного согласования с SAGUR:** принять версию 2 с составным значением `a` как основной формат новых сообщений. Восстановление полной клавиатуры использовать только как совместимый резервный путь для уже отправленных сообщений версии 1. Этот вариант предпочтительнее ранее рассмотренного отдельного поля `n`, поскольку передаёт те же необходимые сведения при меньшем размере JSON. Одностороннее включение версии 2 до письменного согласования не допускается.

### 13.4. Telegram

В модели входящего обратного вызова Telegram поле `callback.message` содержит исходное сообщение, а сообщение предусматривает поле `reply_markup` с текущей встроенной клавиатурой. Метод `editMessageReplyMarkup` заменяет только клавиатуру и не требует изменять текст или вложения сообщения.

Проверенный для текстового сообщения алгоритм, ещё не утверждённый как окончательная рабочая реализация:

1. взять `callback.message.reply_markup.inline_keyboard`;
2. удалить из рядов кнопки `l/d` нужного `interaction_id`;
3. удалить опустевшие ряды;
4. вызвать `callback.message.edit_reply_markup` с оставшейся клавиатурой.

Живое испытание 19 августа 2026 года подтвердило этот алгоритм на текстовом сообщении `l+d / m`, фактически отправленном SAGUR через общий рабочий бот. После `l` Telegram изменил то же сообщение с `[['l', 'd'], ['m']]` на `[['m']]`; текст не изменился, нового сообщения не появилось, сохранённая `m` нажалась два раза. Сообщение с вложением и набор `l+d / c` ещё не проверены. Полный воспроизводимый протокол: `docs/SAGUR_TELEGRAM_INTERACTION_LIVE_TEST_2026-08-19.md`.

### 13.5. VK

Событие VK содержит `peer_id` и `conversation_message_id`. По ним библиотека предоставляет метод `messages.getByConversationMessageId`. Модель возвращаемого сообщения предусматривает поле `keyboard`.

Проверенный для простого текстового сообщения алгоритм:

1. запросить исходное сообщение по `peer_id` и `conversation_message_id`;
2. получить `message.keyboard`;
3. удалить только `l/d` нужного `interaction_id`;
4. сериализовать оставшиеся ряды без изменения кнопки `m` или `c` и её стиля;
5. вызвать `messages.edit` для исходного сообщения.

Живое испытание подтвердило этот алгоритм для текстового сообщения `l+d / m`. VK вернул клавиатуру вместе с выходным полем `author_id`, которое нельзя отправлять обратно в `messages.edit`; после формирования верхнего уровня из разрешённых входных полей `one_time`, `inline`, `buttons` исходное сообщение успешно изменилось на `[[m]]`. Текст сохранился, новое сообщение не создавалось, `m` нажалась два раза. Сообщения с дополнительными вложениями и набор `l+d / c` ещё не проверены. Полный протокол: `docs/SAGUR_VK_INTERACTION_LIVE_TEST_2026-08-20.md`.

### 13.6. MAX

Модель `message_callback` установленной библиотеки MAX предусматривает необязательное исходное сообщение. Его тело содержит список вложений, в котором клавиатура является отдельным вложением. Если сообщение не пришло внутри обратного вызова, библиотека предоставляет `get_message(message_id)`. Для изменения доступны `edit_message` и ответ на обратный вызов.

Проверенный для простого текстового сообщения алгоритм:

1. получить исходное сообщение из события либо отдельным запросом по `mid`;
2. найти среди вложений `inline_keyboard`;
3. удалить из неё кнопки `l/d` нужного `interaction_id`;
4. сохранить все остальные вложения сообщения, включая изображения и файлы;
5. передать обновлённый полный список вложений в операцию изменения сообщения.

Живое испытание подтвердило изменение исходного текстового сообщения MAX с `[['l', 'd'], ['m']]` на `[['m']]`: текст сохранился, новое сообщение не появилось, `m` осталась доступной. Отдельно установлено, что технический ответ и редактирование — разные запросы; пустой низкоуровневый ответ `{}` MAX отклоняет, а штатный `event.answer("")` при наличии исходного сообщения принимает. Сообщения с дополнительными вложениями, разметкой и набор `l+d / c` ещё не проверены. Полный протокол: `docs/SAGUR_MAX_INTERACTION_LIVE_TEST_2026-08-20.md`.

### 13.7. Результат обязательной проверки осуществимости

Удаление `l/d` из исходного текстового сообщения `l+d / m` подтверждено живыми испытаниями Telegram, VK и MAX. В VK при повторной отправке прочитанной клавиатуры необходимо удалять выходное поле `author_id` и формировать верхний уровень по явному списку входных полей. В MAX техническое подтверждение требуется отправлять штатным непустым ответом отдельно от редактирования. Для сообщений с дополнительными вложениями, разметкой и набора `l+d / c` живые испытания не выполнялись; эти варианты должны покрываться безопасным сохранением неизвестных элементов и отдельными автоматическими тестами либо следующим контролируемым испытанием, если код затрагивает их платформенное представление.

Испытание выполняется через рабочие чат-боты на заранее выбранных учётных записях и с теми же токенами и правами, которые использует vtelemax:

1. SAGUR отправляет отдельное контролируемое сообщение с реальной клавиатурой;
2. до нажатия фиксируются идентификатор сообщения, текст, клавиатура и вложения;
3. выбранная учётная запись нажимает `l` либо `d`;
4. из фактического события берутся платформенные идентификаторы исходного сообщения;
5. изолированный проверочный код пытается изменить именно исходное сообщение: удалить `l/d` и сохранить `m` либо `c`;
6. после операции сообщение повторно читается через программный интерфейс и проверяется глазами в клиенте мессенджера;
7. фиксируются ответ платформы, итоговая клавиатура, неизменность текста, сохранность вложений и отсутствие нового дублирующего сообщения.

Минимум для каждой платформы требуется проверить:

1. текстовое сообщение с набором `l,d,m`;
2. сообщение с используемым в реальной рассылке вложением и набором `l,d,c`;
3. редактирование сообщения, фактически отправленного SAGUR через общий рабочий бот, а не искусственно созданного другим ботом;
4. выполнение операции теми полномочиями, которыми будет располагать рабочий vtelemax.

Критерий положительного результата по платформе: исходное сообщение изменено на месте, `l/d` отсутствуют, правильная `m/c` остаётся, текст и вложения не повреждены. Сам факт успешного ответа метода без проверки итогового сообщения положительным результатом не считается.

Решение после испытаний:

1. если операция подтверждена на всех трёх платформах, удаление `l/d` можно рассматривать как реализационный вариант;
2. если операция подтверждена только частично, нельзя объявлять единый алгоритм — требуется отдельно согласовать платформенные различия пользовательского поведения;
3. если операция не подтверждена, требование удаления кнопок нельзя закладывать в разработку как выполнимое; необходимо вернуться к SAGUR с протоколом испытания и пересмотреть пользовательский сценарий.

### 13.8. Безопасное правило при невозможности получить клавиатуру или изменить сообщение

Если исходную клавиатуру получить не удалось, её состав неоднозначен либо платформа не позволила безопасно изменить сообщение:

1. само нажатие всё равно считается зафиксированным и отправляется в SAGUR;
2. нельзя угадывать состав клавиатуры;
3. нельзя выбирать `m` или `c` только по действию `l/d`;
4. нельзя удалять всю клавиатуру, потому что это уничтожит допустимую навигационную кнопку;
5. исходное сообщение нельзя заменять случайным меню;
6. ошибка изменения интерфейса фиксируется отдельно от доставки события.

В таком аварийном случае клавиатура остаётся без изменения. Пользователь может повторно нажать оценку; каждое новое реально полученное нажатие всё равно сохраняется, а SAGUR применяет правило первой оценки.

### 13.9. Итоговый статус пункта

1. **Факт контракта:** после оценки `l/d` должна остаться фактическая кнопка `m` либо `c` исходного набора.
2. **Факт версии 1:** JSON нажатой оценки не сообщает, какой навигационный вариант находился в сообщении.
3. **Предложение владельца проекта для версии 2:** кодировать нажатую кнопку первым символом составного `a`, а остальными символами — весь исходный набор.
4. **Рекомендация по формату события:** совместно с SAGUR утвердить версию 2; чтение полной клавиатуры оставить резервным способом для версии 1.
5. **Подтверждённая осуществимость:** для текстового сообщения `l+d / m` Telegram, VK и MAX позволяют изменить исходное сообщение на месте, удалить `l/d` и сохранить работающую `m`.
6. **Оставшаяся граница доказательства:** сообщения с дополнительными вложениями и вариант `l+d / c` не проходили отдельное живое испытание; они должны быть покрыты автоматическими проверками и, при отличающемся платформенном представлении, контролируемым испытанием.
7. **Следующее действие по контракту:** передать SAGUR точную схему версии 2, закрытый перечень `ldm/dlm/mld/ldc/dlc/cld`, обоснование и требование совместимости с уже отправленной версией 1.
8. **Следующее техническое действие:** реализовать рабочий обработчик на основе проверенных платформенных алгоритмов и отдельно подтвердить сохранность фактических вложений используемых шаблонов.

Проверка платформ больше не должна использоваться как основание для косвенного определения `m/c`: состав набора предлагается передавать непосредственно в версии 2.

## 14. Пакетная отправка событий в SAGUR

Рекомендуемая модель:

1. отправитель запускается примерно раз в пять минут;
2. одна пачка содержит от 1 до 100 событий;
3. необходимо проверять фактический размер тела запроса — не более 65 536 байт;
4. для каждой попытки HTTP-запроса создаётся новый `request_id`;
5. `event_id` каждого события при повторах остаётся прежним;
6. подпись HMAC строится по строке:

```text
METHOD
PATH
TIMESTAMP
SHA256(BODY)
```

7. окончательно подтверждёнными считаются результаты:
   - `accepted`;
   - `duplicate`;
   - `rating_already_recorded`;
8. ошибка одного элемента пачки не должна приводить к повторной отправке уже подтверждённых элементов;
9. проблемный элемент не удаляется, а переводится в диагностируемое состояние;
10. сетевые ошибки, HTTP `429` и временные серверные ошибки повторяются без малого фиксированного предела попыток.

### Почему нельзя без изменений использовать существующий регистр регистрации гостя

Фраза означает запрет на прямое подключение нажатий к существующей таблице и работнику регистрации без изменения их модели. Она не запрещает переиспользовать проверенные инфраструктурные приёмы или выделить из существующего кода общие компоненты.

Текущий отправитель события регистрации:

1. отправляет по одному событию;
2. использует тайм-аут около пяти секунд;
3. после восьми попыток переводит событие в конечную ошибку;
4. не обрабатывает частичные результаты пачки.

Кроме поведения отправителя, существующая таблица регистрации содержит обязательные для регистрации, но посторонние для нажатий поля: пользователя, телефон, происхождение регистрации, состояния iikoCard, результаты создания гостя и сохранённое одиночное тело события. Её `request_id` относится к одному заранее собранному запросу, тогда как для взаимодействий новый `request_id` создаётся на каждую пакетную HTTP-попытку.

Для взаимодействий нужны другие свойства:

1. отдельная строка на каждое новое реальное нажатие без объединения по пользователю;
2. пакет от 1 до 100 разных событий с ограничением 65 536 байт;
3. поэлементный частичный ответ SAGUR;
4. подтверждение и повтор только соответствующих элементов;
5. бессрочное сохранение временно недоставленного события до устранения причины, а не конечная ошибка после восьми попыток;
6. отдельное состояние пользовательского действия, которого нет у события регистрации.

Для нажатий требуются пачки, более длинный тайм-аут, поэлементные результаты и бессрочные повторы временных ошибок. Поэтому существующий механизм можно использовать как образец, но не копировать без изменений.

Полезные части существующего решения:

1. построение подписи HMAC;
2. блокировка строк при конкурентной выборке;
3. восстановление зависших блокировок;
4. организация отдельного фонового работника и транзакционных границ;
5. общие правила безопасных ошибок, журналов и показателей.

Переиспользование должно происходить на уровне небольших общих функций и инфраструктурного шаблона. Превращать существующий специализированный регистр регистрации в универсальную таблицу всех интеграционных событий без отдельного измерения также не следует: это смешает разные жизненные циклы, статусы и правила повторов.

Если отправитель может работать более чем в одном процессе, одного внутрипроцессного замка недостаточно. Нужен один выделенный работник либо межпроцессная блокировка PostgreSQL.

## 15. Обязательная программа проверки

### 15.1. Проверка разбора полезной нагрузки

Положительные примеры утверждённой версии 1, которые нужно продолжать принимать для совместимости:

```json
{"t":"si","v":1,"i":123456,"a":"l"}
{"t":"si","v":1,"i":123456,"a":"d"}
{"t":"si","v":1,"i":123456,"a":"m"}
{"t":"si","v":1,"i":123456,"a":"c"}
```

Отрицательные примеры:

1. неправильный `t`;
2. неизвестная версия `v`;
3. отсутствующий или неположительный `i`;
4. неизвестное действие;
5. обычные кнопки текущего меню;
6. произвольный пользовательский JSON;
7. слишком большая или повреждённая строка.

Если SAGUR утверждает предложенную версию 2, дополнительно проверяются все шесть допустимых значений `a`:

```text
ldm, dlm, mld, ldc, dlc, cld
```

Для версии 2 должны отклоняться односимвольные значения, произвольные перестановки, повторяющиеся символы, смешанный набор `l,d,m,c` и любые значения вне закрытого перечня.

### 15.2. Проверка различения нового нажатия и технического повтора

Для каждой платформы необходимо подтвердить на рабочем боте:

1. идентификатор первого реального нажатия;
2. идентификатор второго реального нажатия той же кнопки;
3. идентификатор повторной доставки того же входящего события, если её удаётся воспроизвести;
4. создание двух строк для двух реальных нажатий;
5. определить фактическое поведение при техническом повторе, если его удаётся воспроизвести;
6. только после этого сформулировать и проверить уникальное ограничение при двух одновременных обработчиках.

### 15.3. Проверка пользовательского интерфейса

Проверка делится на два разных этапа.

**Этап 1 — проверка осуществимости до выбора реализации.** Выполняется по процедуре раздела 13.7 на реальных сообщениях SAGUR во всех трёх рабочих ботах. Пока этот этап не пройден, удаление `l/d` остаётся гипотезой и не включается в утверждённый план разработки.

**Этап 2 — проверка реализованного поведения.** Проводится только если этап 1 подтвердил возможность выбранного способа. На Telegram, VK и MAX проверить:

1. `l` удаляет только `l` и `d`;
2. `d` удаляет только `l` и `d`;
3. `m` открывает главное меню новым сообщением;
4. `c` открывает общий раздел купонов новым сообщением;
5. повторные `m` и `c` создают новые события;
6. старое сообщение рассылки продолжает обрабатываться;
7. сообщение с изображением или другим вложением не повреждается;
8. недоступная клавиатура не приводит к случайной замене сообщения.

### 15.4. Проверка режима поддержки

Для зарегистрированного пользователя проверить:

1. пользователь ожидает ввода вопроса и нажимает `l`;
2. пользователь ожидает ввода вопроса и нажимает `d`;
3. пользователь ожидает ввода вопроса и нажимает `m`;
4. пользователь ожидает ввода вопроса и нажимает `c`;
5. пользователь ожидает ответа поддержки и нажимает каждую из кнопок;
6. история обращения сохраняется;
7. `l` и `d` не меняют состояние поддержки;
8. `m` и `c` отменяют только ожидаемый ввод или контекст ответа.

### 15.5. Проверка доставки в SAGUR

Проверить:

1. одну пачку;
2. более 100 ожидающих событий;
3. ограничение размера тела;
4. правильность HMAC по фактическим байтам тела;
5. новый `request_id` при повторе;
6. неизменный `event_id` при повторе;
7. частичный ответ, где разные элементы имеют разные результаты;
8. `accepted`;
9. `duplicate`;
10. `rating_already_recorded`;
11. ошибку конкретного элемента;
12. HTTP `429`;
13. временную ошибку SAGUR;
14. перезапуск отправителя после захвата строк.

### 15.6. Среда проверки

Отдельных проверочных ботов нет. Сквозная проверка проводится через рабочие чат-боты только на заранее выбранных телефонных номерах и учётных записях. Формулировки о тестовых ботах или тестовом сообществе применять нельзя.

**Подтверждено владельцем проекта 19 августа 2026 года:** устройство с заранее выбранной учётной записью Telegram находится у владельца и доступно для немедленного контролируемого нажатия и визуальной проверки результата. Исходящая отправка двухрядного Telegram-сообщения `l+d / m` со служебным JSON уже была принята Telegram и визуально подтверждена ранее; повторять её без новой проверяемой цели не требуется. Следующая новая проверка Telegram должна охватывать обратный вызов при нажатии и фактическое удаление только `l/d` с сохранением `m` либо `c`.

**Проверено по текущему коду 19 августа 2026 года:** существующее логирование не позволяет выполнить эту проверку без подготовленного перехвата. В Telegram-маршруте зарегистрированы только обработчики с точными фильтрами известных команд; общего обработчика неизвестного обратного вызова нет. Служебный JSON SAGUR не соответствует ни одному фильтру. Текущие журналы известных обработчиков не выводят `callback_query.id`, полный объект исходного сообщения или служебные данные неизвестного нажатия. Внутренний журнал `aiogram` для необработанного обновления содержит только `update_id`, признак `not handled`, длительность и идентификатор бота, но не полезную нагрузку; кроме того, приложение настраивает `loguru`, а не мост стандартного журнала `aiogram`.

Библиотека продвигает `offset` после получения обновления независимо от того, нашёлся ли прикладной обработчик. Поэтому нажатие до установки диагностического перехвата может быть безвозвратно потреблено текущим опросом и не даст необходимых доказательств. Параллельный ручной `getUpdates` запрещён как способ проверки: он конкурирует с рабочим ботом за один поток обновлений и может перехватить чужие события. До контролируемого нажатия требуется минимальный обработчик, ограниченный служебным типом SAGUR и заранее выбранной учётной записью либо идентификатором интерактивности.

**Утверждённая форма одновечерней проверки:** постоянные настройки и новые переменные окружения для диагностического перехвата не добавляются. Создаётся отдельный временный модуль Telegram с точным фильтром одного специально выбранного проверочного `interaction_id`. В действующей сборке выполняются только две явные точки подключения: импорт модуля и регистрация его маршрутизатора перед основным маршрутизатором Telegram. Все несовпадающие события модуль обязан пропускать без ответа и изменения. После проверки подключение и временный файл удаляются; до удаления модуль не должен оставаться развёрнутым дольше согласованного проверочного окна.

**Временная реализация и живое испытание выполнены 19 августа 2026 года:**

1. временный модуль создан в `src/vtelemax/adapters/telegram/sagur_interaction_probe.py`;

### 15.7. Проверка задержки и нагрузки

Одного анализа плана запроса через `EXPLAIN ANALYZE` недостаточно. До выпуска требуется отдельная проверка полного горячего пути на PostgreSQL, а не на SQLite или подменённом репозитории.

Набор проверки:

1. заполнить таблицу числом завершённых строк, соответствующим прогнозному сроку хранения и объёму с запасом;
2. оставить реалистичную долю `pending/retry/processing`;
3. одновременно выполнять новые вставки с разными платформенными ключами;
4. отдельно подавать технические повторы одного ключа;
5. параллельно запускать выборку и подтверждение пачек отправителем;
6. повторить испытание при недоступном SAGUR и большой глубине очереди;
7. выполнять запись с рабочими настройками долговечности PostgreSQL, включая фактическую фиксацию журнала предзаписи;
8. проверить влияние очистки мёртвых версий строк и восстановления просроченных захватов.

Измеряются отдельно:

1. ожидание соединения из пула;
2. длительность `INSERT ... ON CONFLICT`;
3. длительность фиксации транзакции;
4. время от получения обратного вызова до ответа мессенджеру;
5. длительность последующего пользовательского действия;
6. медиана, 95-й и 99-й процентили, максимум, ошибки и превышения времени ожидания;
7. скорость роста таблицы и каждого индекса.

Числовые критерии приёмки фиксируются до выпуска после базового измерения рабочей инфраструктуры. Если критерии не выполняются, сначала исследуется измеренное узкое место; новая таблица, дополнительный кэш или секционирование не добавляются без доказанной причины.

## 16. Выявленные расхождения и риски

### 16.1. Продвижение позиции опроса и повтор события

**Статус: закрыто как установленный технический факт.** Рекомендация «не отвечать на обратный вызов, чтобы платформа повторила событие» не гарантируется текущей реализацией длительного опроса: позиция опроса может быть продвинута независимо от пользовательского ответа. Из этого не следует необходимость менять текущую архитектуру опроса в рамках задачи.

### 16.2. Значение `occurred_at`

**Статус: закрыто решением владельца проекта.** Это серверное время первой успешной локальной фиксации события в vtelemax, а не неизвестное клиентское время физического касания экрана, не время пакетной отправки и не время приёма SAGUR.

### 16.3. Проверочные боты

**Статус: закрыто исправлением терминологии.** Отдельных проверочных ботов нет. Контролируемые испытания выполняются через рабочие боты на заранее выбранных учётных записях.

### 16.4. Отсутствие обработчика JSON SAGUR в текущем vtelemax

**Статус: ожидаемая открытая работа реализации, а не необъяснённое противоречие.** На момент проверки в `src`, `tests` и `migrations` нет обработчика `message_interaction`, полей `interaction_id` или `platform_callback_id` и результата `rating_already_recorded`. Это соответствует тому, что разработка функции ещё не начиналась. До реализации существующие общие обработчики не должны получать новый JSON как обычную команду.

### 16.5. Адрес программного интерфейса и библиотека MAX

**Статус: решение для текущей задачи утверждено владельцем проекта 19 августа 2026 года.** Проект закрепляет `maxapi==0.9.16`; его рабочий маршрут использует `https://platform-api.max.ru`. Через этот адрес реальная исходящая клавиатура уже успешно отправлена и визуально подтверждена. В текущей доработке сохраняется именно этот адрес.

Проверенный новый адрес `https://platform-api2.max.ru` из рабочего контейнера установил TCP-соединение, но не прошёл проверку цепочки сертификата (`VERIFY=20`); отправка через него не состоялась. Его документация, примеры, требования к библиотеке и сертификатам изучаются отдельной будущей задачей и не блокируют текущую разработку.

Открытой проверкой текущей задачи остаётся не выбор адреса, а обратный путь нажатия и возможность изменить исходное сообщение через сохраняемый рабочий адрес `https://platform-api.max.ru`.

### 16.6. Рекомендация MAX использовать веб-перехватчики

**Статус: принятая граница задачи.** Это эксплуатационный риск текущего длительного опроса, но переход на веб-перехватчики не входит в текущую доработку и не выполняется автоматически. Риск фиксируется для будущего развития.

### 16.7. Контекст для автоматического повтора пользовательского действия

**Статус: решение для `m/c` утверждено владельцем проекта 19 августа 2026 года; вопрос `l/d` остаётся отдельной проверкой.** Минимальных полей события достаточно для доставки факта нажатия в SAGUR, но их недостаточно, чтобы после перезапуска гарантированно повторить изменение конкретного сообщения или открытие раздела на каждой платформе. Например, одного `provider_message_id` недостаточно для Telegram без контекста чата.

Если автоматическое восстановление пользовательского действия после перезапуска входит в требования, таблица должна хранить минимальный безопасный платформенный адрес действия и отдельное состояние повтора. Если такое требование не принимается, дополнительный контекст ради гипотетического повтора не сохраняется: ошибка действия фиксируется, кнопка остаётся доступной, пользователь может нажать снова.

Конкретный пример с кнопкой `m`:

1. пользователь нажал «Главное меню»;
2. vtelemax успешно записал событие и зафиксировал транзакцию PostgreSQL;
3. платформа получила технический ответ, поэтому индикатор ожидания на кнопке завершился;
4. до отправки пользователю нового сообщения с главным меню процесс vtelemax аварийно завершился;
5. событие уже существует и позднее будет доставлено в SAGUR, но главное меню пользователь не получил.

Если требуется автоматическое восстановление, после перезапуска работник должен увидеть незавершённое пользовательское действие и отправить меню. Для этого недостаточно знать только идентификатор исходного сообщения: Telegram нужен как минимум адрес чата, VK — адрес диалога, MAX — фактический адрес получателя, поддерживаемый используемым методом. Эти поля должны быть сохранены до сбоя.

Если автоматическое восстановление не требуется, строка сохраняет ошибку или незавершённый статус, автоматическая отправка меню не выполняется. Кнопка `m` остаётся доступной; пользователь может нажать её повторно, и это будет новое реальное событие с новым `event_id`.

Аналогичный случай для `l/d`: событие оценки сохранено, но процесс завершился до изменения клавиатуры. Без автоматического восстановления оценка всё равно уйдёт в SAGUR, а кнопки останутся видимыми и смогут быть нажаты повторно. С восстановлением потребуются адрес исходного сообщения и безопасная повторяемая операция его изменения.

Есть противоположное окно сбоя:

1. vtelemax фактически отправил главное меню пользователю;
2. процесс завершился после успешной отправки, но до фиксации `user_action_status=done`;
3. после перезапуска база всё ещё показывает незавершённое действие;
4. автоматический повтор может отправить второе одинаковое меню.

Поэтому гарантировать «ровно одно» пользовательское действие одной локальной транзакцией нельзя: отправка в мессенджер и запись PostgreSQL не образуют общей транзакции. Автоматический повтор выбирает гарантию «как минимум один раз» с риском дубля; отказ от автоматического повтора выбирает «не более одного раза» с риском пропустить действие при аварии.

Риск различается по действиям:

1. повторное приведение клавиатуры `l/d` к одному и тому же конечному виду потенциально повторяемо безопасно, но это должно быть подтверждено испытанием платформ;
2. повторная отправка нового меню `m` или купонов `c` создаёт видимый дубль и не является безопасно повторяемой операцией.

**Утверждённое решение:** в первой версии не выполнять автоматический повтор `m/c` после неопределённого результата. Если при редкой аварии меню или раздел купонов не появился, навигационная кнопка остаётся доступной, и пользователь повторяет действие осознанно. Повторное нажатие является новым реальным нажатием, поэтому создаёт новую локальную строку и новый `event_id`. Возможность автоматически повторять изменение клавиатуры `l/d` рассматривается отдельно только после подтверждения реального платформенного поведения.

### 16.8. Как состояния и действия устроены в текущем проекте; применимость Redis

**Факты текущего кода:**

1. текущие обработчики обратных вызовов Telegram, VK и MAX сначала отправляют платформе технический ответ на кнопку, затем синхронно вызывают общий адаптер, формируют экран и редактируют исходное сообщение либо отправляют новое;
2. отдельной надёжной строки пользовательского действия, состояния `pending/done` и работника автоматического восстановления меню или купонов сейчас нет;
3. временные состояния регистрации, поддержки, редактирования профиля и модерации хранятся в обычных словарях памяти экземпляра адаптера: Telegram — `_onboarding_state_by_user_id`, `_dialog_state_by_user_id` и связанные словари; VK и MAX — `_state_by_user_id` и связанные словари;
4. после перезапуска процесса содержимое этих словарей теряется;
5. долговечные факты регистрации и согласий сохраняются в PostgreSQL в `person_platform_states`: `rules_accepted`, `notifications_allowed`, `is_registered` и соответствующие даты;
6. Redis присутствует в `pyproject.toml` как зависимость и упомянут в `.env.example`, но в `settings.py`, `docker-compose.yml`, сборке Telegram/VK/MAX и адаптерах не подключён. В `tools/user_reset.py` определены только вспомогательные операции поиска и удаления ключей, которые необязательный ручной сценарий `scripts/reset_test_user.py --clean-redis` может вызвать для очистки. Сам сценарий прямо сообщает, что состояния конечного автомата сейчас находятся в памяти процесса и для полного сброса требуется перезапуск ботов. Это не хранилище состояний работающих ботов.

Следовательно, само наличие зависимости Redis не означает, что состояния регистрации сейчас сохраняются в Redis. Тестовые строки вида `vtelemax:state:telegram:<id>` проверяют только универсальную очистку подходящих ключей и не доказывают существование таких ключей в рабочем приложении.

Redis можно отдельно применить для сохранения временного шага диалога и совместной работы нескольких экземпляров бота. Для этого пришлось бы перенести не только имя состояния, но и связанные черновики, идентификаторы обращений и контекст модерации, определить срок жизни, политику очистки и режим долговечности Redis. Это отдельное архитектурное изменение.

Redis не устраняет неопределённость автоматического повтора `m/c`, потому что запись в Redis и отправка сообщения через внешний программный интерфейс мессенджера не образуют общей транзакции. Пример:

1. в Redis записано `menu_pending`;
2. мессенджер успешно принял и показал главное меню;
3. процесс завершился до записи `menu_done`;
4. после перезапуска Redis по-прежнему содержит `menu_pending`;
5. автоматический повтор создаст второе меню.

Если сначала отправить меню, а потом создать запись Redis, остаётся обратное окно: процесс может завершиться после отправки и до записи. Поэтому Redis способен хранить намерение и временное состояние, но сам по себе не доказывает, было ли внешнее действие уже выполнено. Для событий нажатия надёжным источником истины остаётся PostgreSQL; решение не повторять `m/c` автоматически устраняет риск видимого дубля ценой редкого пропуска, который пользователь исправляет повторным нажатием.

## 17. Сводка уже согласованных решений

1. Ответы и документация ведутся на русском языке; английские термины используются только при необходимости в скобках.
2. Незарегистрированный пользователь не получает рассылку.
3. Зарегистрированный пользователь может получить рассылку во время взаимодействия с поддержкой.
4. Пользователь может нажимать кнопки сколько угодно раз.
5. Каждое реальное нажатие создаёт отдельное событие и передаётся в SAGUR.
6. По смыслу контракта технический повтор не является новым нажатием. Новые реальные нажатия на всех трёх платформах получили разные идентификаторы, но поведение идентификатора при технической повторной доставке ещё не подтверждено.
7. `interaction_id` создаётся SAGUR для одного конкретного сообщения одному конкретному получателю.
8. Все кнопки одного сообщения имеют одинаковый `interaction_id`.
9. `event_id` создаётся vtelemax отдельно для каждого нового реального нажатия.
10. `occurred_at` — серверное время первой успешной локальной фиксации.
11. `l` и `d` не изменяют состояние поддержки и убирают только кнопки оценки.
12. `m` и `c` являются осознанной навигацией и отменяют только ожидаемый ввод или контекст ответа поддержки.
13. Обращение и история поддержки при этом не удаляются.
14. `m` открывает существующее главное меню новым сообщением без имитации `/start`.
15. `c` открывает общий раздел купонов новым сообщением.
16. Переход на веб-перехватчики не входит в текущую задачу.
17. Проверка выполняется на рабочих ботах с выбранными учётными записями.
18. Ответ на обратный вызов кнопки и продвижение позиции опроса — разные операции.
19. Отсутствие ответа на кнопку не гарантирует повторную доставку события при текущем опросе.
20. Из этого факта не следует обязательная переделка `offset`, `ts` или `marker`.
21. Для локального события нажатия и его текущего состояния доставки используется одна таблица; отдельная таблица очереди в первую версию не вводится.
22. Синхронная обработка нажатия не обращается в SAGUR и не просматривает историю; после одной атомарной локальной вставки и фиксации транзакции бот немедленно завершает ожидание кнопки.
23. В текущей доработке MAX продолжает использовать проверенный адрес `https://platform-api.max.ru`; изучение и переход на `https://platform-api2.max.ru` выносятся в отдельную будущую задачу.
24. После неопределённого результата или перезапуска `m/c` автоматически не повторяются; навигационная кнопка остаётся доступной, а повторное осознанное нажатие пользователя создаёт новое событие и новый `event_id`.
25. При недоступности PostgreSQL пользовательское действие не выполняется, кнопки сохраняются, пользователю показывается ошибка и предлагается повторить нажатие вручную; автоматическое восстановление первоначального нажатия в текущую задачу не входит.

## 18. Открытые решения перед реализацией

Выбор между вариантами A, B и C **не является установленным обязательным решением владельца проекта**. Такой выбор потребуется только при появлении отдельного явного требования автоматически восстанавливать нажатия, пришедшие во время недоступности PostgreSQL. До этого текущий опрос нельзя считать препятствием для реализации обычного успешного сценария.

Решение по платформенным идентификаторам для схемы таблицы:

1. выполнено: Telegram, VK и MAX выдали разные платформенные идентификаторы двум последовательным реальным нажатиям одной `m`;
2. утверждено: сочетание `platform + bot_scope + platform_callback_id` является уникальным ключом первой версии;
3. повторная вставка того же ключа не создаёт новую строку и новый `event_id`; новый ключ создаёт отдельное событие;
4. остаётся неизвестным: с каким идентификатором приходит техническая повторная доставка, если она возможна;
5. если технический повтор получит новый идентификатор, он неотличим от нового реального нажатия; этот допустимый риск отражается в письменном ответе SAGUR, а приоритетом остаётся недопущение потери реального нажатия.

Подтверждённая граница текущей архитектуры: гарантированной точкой локального приёма является успешная запись в PostgreSQL. При её недоступности нельзя сообщать об успешной фиксации. Возможность показать ошибку и оставить клавиатуру допускает ручное повторное нажатие пользователя, но не является автоматическим восстановлением первоначального события.

Технические решения и проверки этапа реализации:

1. фактическая возможность изменить исходное сообщение SAGUR и удалить `l/d`: для текстовых сообщений Telegram, VK и MAX с `l+d / m` подтверждена; для сообщений с дополнительными вложениями и `l+d / c` остаётся открытой;
2. выполнено: SAGUR письменно утвердил версию 2 с закрытым перечнем `ldm`, `dlm`, `mld`, `ldc`, `dlc`, `cld`; версия 1 сохраняется для совместимости;
3. автоматическое удаление и архивирование в первой версии не выполняются; ожидаемое число нажатий в сутки остаётся входом для нагрузочной проверки и наблюдаемости, а не условием выбора срока хранения;
4. требуется ли долговечная история каждой HTTP-попытки либо достаточно счётчика, последней ошибки и структурированных журналов;
5. числовые критерии задержки и нагрузочная проверка утверждённой однотабличной схемы на прогнозном объёме; `EXPLAIN ANALYZE` используется только как часть проверки, а не как единственное доказательство;
6. точное имя таблицы и перечень безопасно сохраняемых платформенных идентификаторов;
7. допустим и безопасен ли автоматический повтор изменения клавиатуры `l/d` после перезапуска; для `m/c` автоматический повтор отклонён;
8. один выделенный отправитель или межпроцессная блокировка PostgreSQL;
9. точные состояния локальной доставки и ошибок;
10. выполнено: обратное нажатие, изменение сообщения и техническое подтверждение MAX проверены через утверждённый для текущей задачи адрес `https://platform-api.max.ru`.
