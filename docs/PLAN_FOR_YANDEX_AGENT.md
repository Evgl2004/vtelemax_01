# План для агента Яндекс

## Контекст
Проект `vtelemax` — монорепозиторий для трёх ботов (Telegram, VK, MAX) с единым ядром strict identity. Текущая ветка разработки — `sourcecraft/develop-yai`. Выполнены работы по паритету UI (P0, P1, P2) согласно спецификации `PARITY_SPEC_V1.md`. Однако в процессе тестирования на сервере обнаружено критическое расхождение: сценарий регистрации в `vtelemax` завершается после отправки телефона, тогда как в оригинальных прототипах (aiogram_01, vkbottle, maxbot_01) после телефона следует многошаговый сбор профиля (FMS): имя, фамилия, пол, дата рождения, email, подтверждение анкеты, согласие на уведомления, регистрация в iiko.

Это расхождение нарушает ожидания пользователей и требует исправления.

## Цель
Разработать и внедрить полный сценарий регистрации (FMS) в `vtelemax`, обеспечив паритет с оригинальными ботами по функциональности и UX, с сохранением архитектурных принципов strict identity.

## Текущее состояние
### Модель данных
- `Person` содержит только `phone_e164` и `accounts`.
- Таблица `persons` в БД не имеет полей профиля.
- Нет таблиц для хранения имени, фамилии, пола, даты рождения, email, согласий.

### Onboarding-сценарий
- Состояния: `WAITING_RULES_CONSENT`, `WAITING_PHONE`, `WAITING_LEGACY_PHONE`.
- После успешной отправки телефона регистрация завершается, пользователь переходит в главное меню.

### Адаптеры
- Обрабатывают только шаги правил и телефона.
- Нет обработки ввода текста (имя, фамилия, email) и выбора (пол, дата рождения, уведомления).

## Задачи

### 1. Расширение модели данных
- Добавить в `core/models.py` поля профиля (опциональные):
  - `first_name: str | None`
  - `last_name: str | None`
  - `gender: Literal["male", "female"] | None`
  - `birth_date: date | None`
  - `email: str | None`
  - `notifications_allowed: bool | None`
  - `notifications_allowed_at: datetime | None`
  - `rules_accepted: bool` (уже есть логически, но не хранится)
  - `rules_accepted_at: datetime | None`
- Создать миграцию БД (добавить колонки в таблицу `persons` или создать отдельную `person_profiles`).
- Обновить репозитории (`postgres/repository.py`) для сохранения и загрузки этих полей.

### 2. Расширение состояний onboarding
- В `core/onboarding.py` добавить новые `OnboardingState`:
  - `WAITING_FIRST_NAME`
  - `WAITING_LAST_NAME`
  - `WAITING_GENDER`
  - `WAITING_BIRTH_DATE`
  - `WAITING_EMAIL`
  - `WAITING_PROFILE_REVIEW`
  - `WAITING_NOTIFICATIONS_CONSENT`
  - `WAITING_IIKO_REGISTRATION`
- Расширить `OnboardingFlowService` методами для обработки каждого шага.
- Определить переходы между состояниями (линейный flow с возможностью редактирования).

### 3. Контент для новых шагов
- В `core/guest_content.py` добавить функции построения экранов:
  - `build_first_name_screen()`
  - `build_last_name_screen()`
  - `build_gender_screen()`
  - `build_birth_date_screen()`
  - `build_email_screen()`
  - `build_profile_review_screen()`
  - `build_notifications_consent_screen()`
- Добавить константы для кнопок (например, "Мужской", "Женский", "Изменить", "Всё верно").
- Учесть платформенные особенности (например, в VK пол выбирается текстовыми кнопками, в Telegram — inline).

### 4. Обновление адаптеров
- Для каждого адаптера (Telegram, VK, MAX) добавить обработку новых состояний:
  - Текстовый ввод (имя, фамилия, дата рождения, email) через `message_handler`.
  - Выбор пола и уведомлений через callback.
  - Подтверждение анкеты (кнопки "Всё верно"/"Изменить").
- Интеграция с iiko: после согласия на уведомления вызвать `iiko_client.register_user` и обработать результат (успех/ошибка).
- Обновить `identity_adapter` и `router` для поддержки расширенного FSM.

### 5. Тестирование
- Написать unit-тесты для новых методов `OnboardingFlowService`.
- Расширить adapter-contract тесты для проверки новых экранов и кнопок.
- Добавить интеграционные тесты полного сценария регистрации.
- Проверить негативные сценарии (невалидный ввод, отмена, таймауты).

### 6. Миграция данных
- Существующие пользователи (уже зарегистрированные) должны иметь `NULL` в новых полях.
- Предусмотреть возможность дозаполнения профиля через команду `/profile` (отдельная задача).

### 7. Документация
- Обновить `PARITY_SPEC_V1.md`, добавив пункты 11–18 для полного сценария регистрации.
- Обновить `DEVELOPMENT_YA_LOG.md` с отчётом о выполнении.
- Создать/обновить `ARCHITECTURE.md` с описанием расширенной модели.

## Приоритеты и этапы
Работу разбить на три этапа:

### Этап 1 (P1 — основа)
- Расширение модели и БД (миграция).
- Добавление состояний и контента для имени, фамилии, пола.
- Обновление адаптеров для обработки этих шагов.
- Тестирование.

### Этап 2 (P2 — продолжение)
- Добавление даты рождения, email, подтверждение анкеты.
- Реализация редактирования полей.
- Тестирование.

### Этап 3 (P3 — завершение)
- Согласие на уведомления.
- Интеграция с iiko (регистрация/обновление).
- Финальное тестирование и smoke-проверка на сервере.

## Ограничения и риски
- **Время**: полная реализация может занять 2–3 недели.
- **Сложность**: необходимо сохранить обратную совместимость с существующими пользователями.
- **Интеграция с iiko**: может потребовать доработки `iiko_client` и обработки ошибок.
- **Платформенные различия**: VK не поддерживает `request_contact`, нужно использовать текстовый ввод для всех полей.

## Критерии успеха
1. Новый пользователь проходит полный сценарий регистрации, как в оригинальных ботах.
2. Все данные профиля сохраняются в БД и могут быть использованы для интеграции с iiko.
3. Существующие пользователи не теряют функциональность.
4. Все тесты проходят.
5. Smoke-проверка на сервере успешна для всех трёх платформ.
