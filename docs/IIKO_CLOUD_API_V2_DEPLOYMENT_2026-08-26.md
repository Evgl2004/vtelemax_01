# Развёртывание авторизации iiko Cloud API v2 от 26.08.2026

## 1. Итог

Производственные процессы `vtelemax`, использующие iiko, переведены с
`IIKO_AUTH_VERSION=v1` на `IIKO_AUTH_VERSION=v2`.

На момент завершения проверки подтверждено:

- все пять целевых контейнеров работают в режиме `v2`;
- число перезапусков каждого контейнера равно нулю;
- завершений из-за нехватки памяти не было;
- новый шлюз получил маркер `v2` и нашёл существующего гостя из каждого
  контейнера;
- локальный кэш маркера создан во всех пяти проверочных вызовах;
- пользовательский сценарий просмотра баланса в Telegram успешно вернул сумму;
- после переключения в журналах не обнаружены трассировки, ошибки уровней
  `ERROR` и `CRITICAL`, а также ошибки iiko.

Ручные пользовательские проверки VK и MAX отложены до появления доступа к
зарегистрированным тестовым учётным записям. Изменяющий сценарий выпуска
виртуальной карты намеренно не запускался.

## 2. Область изменения

Рабочий каталог сервера: `/var/www/vtelemax`.

Пересозданы только процессы, непосредственно создающие шлюз iiko:

- `telegram-bot`;
- `vk-bot`;
- `max-bot`;
- `profile-sync-worker`;
- `sagur-registration-events-worker`.

PostgreSQL, nginx, Xray, службы доставки сообщений, API SAGUR и остальные
контейнеры не пересоздавались.

## 3. Исходное состояние

Перед развёртыванием все контейнеры проекта находились в состоянии `Up`.
Целевые процессы работали на старых образах и не содержали реализации `v2`:
внутри них отсутствовали `IIKO_AUTH_VERSION` и метод
`_get_access_token_v2`.

В защищённом `.env` были заполнены без вывода значений:

- старый `IIKO_API_KEY`;
- `IIKO_APP_ID`;
- `IIKO_CLIENT_SECRET`;
- `IIKO_CLOUD_API_KEY`;
- `IIKO_ORG_ID`;
- `IIKO_AUTH_URL`;
- `IIKO_BASE_URL`.

Compose передавал полный набор переменных каждому из пяти сервисов, а активным
режимом оставался `v1`.

## 4. Проверки до переключения

До изменения рабочего режима выполнены следующие проверки:

1. Перенесённые файлы содержат реализацию `v2` и проходят синтаксическую
   компиляцию Python.
2. Отдельный запрос авторизации `v2` вернул HTTP 200 и непустой маркер. Эта
   проверка использовалась только как подтверждение реквизитов, а не как
   доказательство готовности приложения.
3. Новый образ `telegram-bot` изолированно создал шлюз в режиме `v1`.
4. Через новый шлюз в изолированном контейнере существующий гость успешно найден
   сначала в `v1`, затем в `v2`.
5. Для ответа гостя подтверждено наличие идентификатора и корректный разбор
   баланса и карт без вывода персональных данных.
6. Два последовательных запроса маркера в одном шлюзе `v2` вернули одно и то же
   кэшированное значение с неизменившимся сроком действия.
7. Все пять новых образов создали настроенный шлюз в режиме `v1` и содержали код
   `v2`.

Телефон существующего гостя вводился скрыто через `read -rsp`, передавался во
временную переменную окружения проверочного процесса и удалялся после проверки.
Телефон, маркеры, ключи, идентификатор гостя и сумма баланса в вывод не попадали.

## 5. Развёртывание нового кода в режиме v1

Пять целевых сервисов сначала пересозданы с новым кодом при сохранённом
`IIKO_AUTH_VERSION=v1`.

После запуска подтверждено:

- каждый контейнер имеет состояние `running`;
- `RestartCount=0`;
- значение окружения и значение `AppSettings` равны `v1`;
- интеграция iiko считается настроенной;
- реализация `v2` присутствует;
- в 53 строках журналов не обнаружены трассировки, ошибки уровней `ERROR` и
  `CRITICAL` или ошибки iiko.

Таким образом, обратная совместимость нового кода со старой авторизацией была
проверена до производственного переключения.

## 6. Переключение на v2

Перед изменением создана резервная копия:

`/var/www/vtelemax/.env.before-iiko-v2-20260826`.

В копии сохранено `IIKO_AUTH_VERSION=v1`. В рабочем `.env` изменена только
строка режима на `IIKO_AUTH_VERSION=v2`. Развёрнутая конфигурация Compose
подтвердила `v2` для всех пяти сервисов до их пересоздания.

Сервисы пересозданы без запуска зависимостей и без повторной сборки образов:

```bash
sudo docker compose up -d --no-deps --force-recreate telegram-bot vk-bot max-bot profile-sync-worker sagur-registration-events-worker
```

## 7. Проверки после переключения

После перехода подтверждено:

- все пять контейнеров имеют состояние `running`;
- `RestartCount=0`;
- `OOMKilled=false`;
- `ExitCode=0`;
- переменная окружения и `AppSettings` имеют значение `v2`;
- интеграция iiko настроена и код `v2` загружен;
- из каждого контейнера успешно выполнен безопасный `customer/info` для
  существующего гостя;
- каждый шлюз получил маркер и создал локальный кэш;
- первый контроль 31 строки журналов не выявил ошибок;
- реальный запрос баланса через Telegram показал сумму гостю;
- повторный контроль 28 строк журналов после пользовательского запроса не
  выявил ошибок.

Дополнительная проверка журналов VK и MAX показала соответственно 5 и 3 строки
за выбранное окно. В обоих контейнерах по одному разу подтверждены инициализация
и запуск слушателя; предупреждения, ошибки, коды iiko и необработанные завершения
отсутствуют. Пользовательские сообщения и обратные вызовы после перезапуска в
этом окне не поступали, поэтому журналы подтверждают готовность слушателей, но
не заменяют отложенную интерфейсную проверку.

Изменяющие методы создания гостя, обновления профиля и выпуска карты в рамках
проверки не вызывались.

## 8. Ресурсы сервера

Во время развёртывания сервер имел один процессор, 962 МиБ оперативной памяти и
2 ГиБ подкачки. На контрольном снимке было доступно 275 МиБ памяти, занято около
1 ГиБ подкачки, корневой раздел заполнен на 84 процента, свободно 2,7 ГиБ.

Пятисекундная проверка `vmstat` показала преимущественно 95–98 процентов простоя
процессора. Зафиксирован единичный возврат около 4 МиБ из подкачки с кратким
ожиданием диска; постоянного обмена с подкачкой, очереди процессов или устойчивой
дисковой задержки не обнаружено.

Рекомендуется отдельно контролировать свободное место и доступную память. Эти
ограничения не стали препятствием для текущего переключения.

## 9. Операционное отклонение

После сборки образов была предпринята лишняя попытка создать резервные теги для
старых образов контейнеров. Первый же вызов завершился ответом Docker
`No such image`, после чего включённый в интерактивной оболочке `set -e`
завершил SSH-сеанс.

Команда не перезапускала и не удаляла контейнеры. После повторного входа все пять
процессов оставались `Up` с прежним временем работы. Резервные теги созданы не
были. Данный способ исключён из процедуры: `set -e` не должен включаться в
интерактивной производственной SSH-сессии, а непроверенные операции резервного
тегирования не относятся к переходу версии авторизации.

## 10. Откат

Автоматического возврата на `v1` нет. При подтверждённой проблеме следует
изменить только режим и пересоздать те же пять сервисов:

```bash
sudo sed -i 's/^IIKO_AUTH_VERSION=v2$/IIKO_AUTH_VERSION=v1/' .env && sudo docker compose up -d --no-deps --force-recreate telegram-bot vk-bot max-bot profile-sync-worker sagur-registration-events-worker
```

Если рабочий `.env` будет повреждён, для ручного восстановления сохранена копия
`.env.before-iiko-v2-20260826`. Копирование всей резервной версии поверх рабочего
файла допустимо только после проверки, что после создания копии в `.env` не
появились другие необходимые изменения.

Старый `IIKO_API_KEY` сохраняется до отдельного решения о завершении периода
стабилизации и удалении поддержки `v1`.

## 11. Незавершённые проверки

После появления подходящих тестовых учётных записей необходимо отдельно
проверить отображение баланса в интерфейсах VK и MAX. Проверку виртуальной карты
следует выполнять только для гостя с уже существующей картой либо после явного
разрешения на изменяющий выпуск карты.
