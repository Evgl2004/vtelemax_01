## 2. Краткий итог

1. Проект использует именно iiko Cloud API с адресом
   `https://api-ru.iiko.services`.
2. Проект использует старую авторизацию:
   `POST https://api-ru.iiko.services/api/1/access_token`.
3. В запрос передаётся тело `{"apiLogin": ...}`.
4. Значение для `apiLogin` берётся из переменной `IIKO_API_KEY`.
5. Следовательно, по назначению исполняемого кода `IIKO_API_KEY` является старым
   `apiLogin`, несмотря на вводящее в заблуждение имя. Фактическое значение секрета
   не читалось и не выводилось.
6. От старой авторизации зависят:
   - получение баланса;
   - получение виртуальных карт;
   - создание и обновление клиента;
   - выпуск карты;
   - подключение к программе лояльности;
   - финальный шаг регистрации в Telegram, VK и MAX;
   - дозаполнение старого профиля;
   - фоновая синхронизация профиля;
   - восстановление регистрационных событий SAGUR;
   - ручная проверка iiko в диагностическом скрипте.
7. Рабочие методы iiko должны остаться на `/api/1`. Меняется только адрес и
   контракт получения маркера доступа.
8. Проект технически попадает под обязательный переход, если интеграция включена в
   рабочем окружении.
9. Фактическое использование текущего кода и секретов на рабочем сервере локально
   не доказано.
10. Для внедрения принята временная двухрежимная схема: в переходной версии кода
    будут доступны старая авторизация `v1` и новая авторизация `v2`.
11. В каждый момент процесс использует только один явно выбранный режим. Параллельная
    авторизация и автоматический возврат с `v2` на `v1` запрещены.
12. Сначала двухрежимная версия развёртывается с активным `v1`, затем `v2`
    проверяется отдельно и включается переменной `IIKO_AUTH_VERSION`.
13. После согласованного периода стабильности `v1`, старый секрет и временный
    переключатель удаляются отдельным изменением.

## 3. Официальный контракт

Проверенные официальные источники:

- инструкция iiko:
  <https://ru.iiko.help/articles/#!api-documentations/polucheniyu-dostupa-k-api>;
- спецификация iiko Cloud API:
  <https://api-ru.iiko.services/api-docs/docs>.

Спецификация, прочитанная 26 августа 2026 года, подтверждает:

- `/api/1/access_token` помечен как устаревший;
- новый адрес — `/api/v2/access_token`;
- метод — `POST`;
- обязательные поля запроса — `appId`, `clientSecret`, `apiKey`;
- успешный ответ содержит обязательные `token` и `correlationId`;
- `token` является JWT;
- срок действия — один час;
- точное время окончания действия находится в поле `exp` JWT;
- механизма обновляющего маркера нет;
- рабочие запросы используют `Authorization: Bearer {token}`;
- `apiKey` определяет доступные организации;
- при перевыпуске `clientSecret` прежний секрет немедленно отзывается.

Точная дата окончательного отключения старой точки в прочитанной спецификации не
указана. Отсутствие даты нельзя считать гарантией продолжения работы старого метода.

## 7. Реализация HTTP-клиента

Основной клиент находится в
`src/vtelemax/infrastructure/iiko_client.py`.

Полный URL формируется в строке 335 как:

```text
{IIKO_BASE_URL}{path}
```

Фактический HTTP-вызов выполняется через `urllib.request.urlopen` в строке 342.

Для рабочих запросов устанавливается:

```text
Authorization: Bearer {token}
Content-Type: application/json
```

Время ожидания по умолчанию — 10 секунд.

### 7.1. Старая авторизация

`src/vtelemax/infrastructure/iiko_client.py:285-319`:

1. Проверяется локальный кэш.
2. При отсутствии действующего состояния вызывается `/access_token`.
3. Передаётся `{"apiLogin": self._api_key}`.
4. `self._api_key` заполняется из `IIKO_API_KEY`.
5. Из ответа извлекается `token`.
6. Маркер кэшируется на фиксированные 14 минут.

При стандартном базовом адресе итоговый URL однозначно равен:

```text
POST https://api-ru.iiko.services/api/1/access_token
```

Именно способ использования, а не имя переменной, доказывает, что существующий
секрет предназначен для поля `apiLogin`.

## 9. Достижимые сценарии

### 9.1. Получение баланса

Цепочка:

```text
входящее сообщение или нажатие
→ маршрутизатор платформы
→ платформенный адаптер
→ действие BALANCE
→ GetLoyaltyBalanceUseCase.execute
→ IikoLoyaltyGateway.get_customer_info
→ получение маркера
→ POST customer/info
→ walletBalances
→ пользовательский экран баланса
```

Точки обработки:

- Telegram: `identity_adapter.py:3040-3084`;
- VK: `identity_adapter.py:2875-2904`;
- MAX: `identity_adapter.py:2770-2799`;
- общий сценарий: `core/loyalty_use_cases.py:117-166`.

Если клиент не найден или шлюз вернул ошибку, формируется `IIKO-BAL-001`. В
платформенном адаптере может создаваться автоматическое обращение поддержки.

### 9.2. Получение или выпуск виртуальной карты

Цепочка:

```text
действие VIRTUAL_CARD
→ GetVirtualCardUseCase.execute
→ customer/info
→ если клиента нет: customer/create_or_update
→ если карт нет: customer/card/add
→ loyalty/iiko/program
→ при найденной программе: customer/program/add
→ повторный customer/info
→ номера карт
→ QR-коды и пользовательский экран
```

Общий сценарий расположен в `core/loyalty_use_cases.py:169-296`.

Возвращаемый `customer_id` используется для выпуска карты и для регистрационного
контура SAGUR. Номера карт передаются маршрутизаторам платформ для формирования
QR-кодов.

### 9.3. Финальный шаг регистрации

В Telegram, VK и MAX после получения согласия на уведомления локальный профиль
сохраняется с `is_registered=True`, затем запускается финальная iiko-синхронизация.

Цепочка:

```text
согласие пользователя
→ локальное сохранение зарегистрированного профиля
→ состояние WAITING_IIKO_SYNC
→ поиск или создание клиента iiko
→ обновление профиля
→ выпуск карты
→ подключение программы
→ QR-коды
→ главное меню
```

Точки:

- Telegram: `adapters/telegram/identity_adapter.py:760-850` и `3770-3809`;
- VK: `adapters/vk/identity_adapter.py:940-1078`;
- MAX: `adapters/max/identity_adapter.py:830-965`.

Если шлюз подключён, но вызов iiko не дал карту, пользователь остаётся на экране
повторной синхронизации. Если шлюз вообще не подключён, финальный шаг пропускается и
регистрация завершается без карты.

Это означает, что настроенная, но неработающая авторизация влияет сильнее, чем явно
выключенная интеграция.

### 9.4. Дозаполнение старого профиля

После подтверждения телефона старого пользователя вызывается `customer/info`.
Пустые локальные поля могут быть дополнены следующими значениями из iiko:

- имя;
- фамилия;
- пол;
- дата рождения;
- электронная почта.

Уже заполненные локальные поля не перезаписываются.

Точки:

- Telegram: `identity_adapter.py:3716-3768`;
- VK: `identity_adapter.py:3301` и последующий метод;
- MAX: `identity_adapter.py:3226-3278`.

Ошибка iiko на этом шаге не блокирует сценарий: дозаполнение пропускается. Поздняя
финальная синхронизация при подключённом шлюзе уже может заблокировать интерфейс.

### 9.5. Фоновая синхронизация профиля

После успешного редактирования профиля платформенный адаптер ставит задачу в
`profile_sync_queue` при подключённом сценарии очереди.

Точки постановки:

- Telegram: `identity_adapter.py:2196-2232`;
- VK: `identity_adapter.py:1800-1835`;
- MAX: `identity_adapter.py:1693-1728`.

Фоновый обработчик запускается только при `PROFILE_SYNC_ENABLED=true` и наличии
полной текущей конфигурации iiko.

Обработка `adapters/profile_sync.py:24-138`:

```text
pending-задача
→ чтение локального профиля
→ customer/info
→ получение customer_id, если клиент найден
→ customer/create_or_update
→ done либо повтор с задержкой либо failed
```

Максимальное число попыток по умолчанию — пять.

### 9.6. Регистрационный контур SAGUR

При включённом `SAGUR_REGISTRATION_EVENTS_ENABLED` финальная синхронизация
регистрации оборачивается в `SagurRegistrationFinalizationService`.

При успешном результате iiko и наличии `customer_id` создаётся ожидающее событие
SAGUR. Если авторизация iiko не работает, событие не создаётся.

### 9.7. Восстановление неизвестного результата

При включённых:

- `SAGUR_REGISTRATION_EVENTS_ENABLED`;
- `SAGUR_REGISTRATION_EVENTS_RECOVERY_ENABLED`;
- HMAC-секрете SAGUR;
- конфигурации iiko;

обработчик `SagurRegistrationRecoveryProcessor` выполняет только `customer/info` для
проблемных записей. Клиент фоном не создаётся.

Точка: `adapters/sagur_registration_events.py:368-474`.

При найденном клиенте сохраняется `customer_id` и создаётся ожидающее событие SAGUR.
При ошибке выполняются ограниченные повторы, затем запись требует ручной обработки.

### 9.8. Диагностический скрипт

`scripts/diagnose_iiko_balance_incident.py` является ручной административной
утилитой и не подключён к штатным точкам запуска.

Без флага `--live-iiko-readonly` скрипт не обращается к iiko. При наличии флага он:

1. читает текущий `.env`;
2. получает старый маркер по `apiLogin`;
3. выполняет только `customer/info`;
4. не создаёт и не изменяет клиента или карту.

Скрипт содержит собственную реализацию авторизации, поэтому его необходимо изменить
отдельно либо перевести на общий клиент.

## 10. Обработка ответов

### 10.1. Маркер доступа

Текущий код:

- требует HTTP 200;
- извлекает поле `token`;
- отклоняет пустой `token`;
- игнорирует `correlationId`;
- кэширует маркер на 14 минут;
- не читает время действия из ответа или JWT.

### 10.2. Клиент

`customer/info` преобразуется в `LoyaltyCustomer`:

- `id` → `customer_id`;
- выбранный `walletBalances[].balance` → баланс;
- `cards[]` → карты;
- имя, фамилия, пол, дата рождения и электронная почта → профиль.

HTTP 400 и 404 считаются отсутствием клиента. Другие статусы превращаются в
`LoyaltyGatewayError`.

### 10.3. Создание или обновление

Успешный ответ должен содержать `id`. Пустой `id` считается ошибкой.

### 10.4. Выпуск карты и программа

Неуспешный выпуск карты является ошибкой сценария. Ошибка получения или подключения
программы не отменяет уже выпущенную карту и возвращает частично успешное сообщение.

## 11. Недостатки текущего клиента

1. Один `IIKO_BASE_URL` используется для авторизации и рабочих методов.
2. Нельзя заменить `/api/1` на `/api/v2` глобально.
3. Имя `IIKO_API_KEY` не соответствует назначению старого секрета.
4. Нет `appId` и `clientSecret`.
5. Кэш использует фиксированные 14 минут.
6. Нет чтения JWT `exp`.
7. Нет потоковой блокировки при обновлении маркера.
8. Несколько потоков могут одновременно запросить новый маркер.
9. При HTTP 401 кэш не очищается.
10. Нет однократной повторной авторизации после 401.
11. Нет встроенных ограниченных повторов при 408, 429, 5xx и сетевых ошибках.
12. `correlationId` не сохраняется.
13. Некорректный JSON превращается в пустой объект без отдельной причины ошибки.
14. В отдельных ошибках и предупреждениях используется необработанное тело ответа.
15. Для некоторых операций текст внутренней ошибки попадает в пользовательское
    сообщение.
16. Нет тестов контракта авторизации, кэша, истечения, 401 и конкуренции.

Дополнительный риск: клиент синхронный. Платформенные обработчики вызывают его из
сценариев обработки сообщений. Длинные повторы могут увеличить блокировку обработки
сообщений, поэтому число попыток и задержки должны быть небольшими.

## 12. Текущее тестовое покрытие

Существующие тесты покрывают:

- преобразование ответа клиента;
- тело `create_or_update`;
- отсутствие клиента при 400/404;
- часть диагностических метаданных;
- бизнес-сценарии баланса и виртуальной карты;
- регистрацию и повтор после ошибки iiko в трёх адаптерах;
- очередь синхронизации профиля;
- часть регистрационного контура SAGUR;
- признак `is_iiko_configured`.

Не покрыты:

- старое и новое тело авторизации;
- полный URL авторизации;
- успешное получение маркера;
- поле `correlationId`;
- JWT `exp`;
- истечение и обновление маркера;
- HTTP 401 и однократный повтор;
- HTTP 408, 429, 5xx;
- сетевой тайм-аут;
- отсутствие или некорректный JSON авторизации;
- отсутствие `token`;
- одновременное получение маркера;
- отсутствие секретов в журналах;
- явная гарантия сохранения рабочих адресов `/api/1`.

Тесты во время анализа не запускались, чтобы не изменять рабочее окружение и
сохранить режим только чтения.

## 13. Оценка влияния отключения старой авторизации

### 13.1. Баланс

Баланс полностью перестанет загружаться для новых и существующих пользователей.
Локального кэша баланса нет. Пользователь получит `IIKO-BAL-001`, а платформенный
адаптер может создать автоматическое обращение поддержки.

### 13.2. Виртуальная карта

Перестанут работать:

- поиск существующей карты;
- показ номера и QR-кода;
- создание клиента;
- обновление клиента;
- выпуск карты;
- подключение программы лояльности.

### 13.3. Новая регистрация

При настроенном шлюзе локальный профиль будет сохранён как зарегистрированный, но
пользовательский сценарий останется на шаге повторной синхронизации iiko.

Проблема затрагивает Telegram, VK и MAX.

### 13.4. Старые пользователи

Дозаполнение из iiko будет пропущено. Само по себе это не блокирует сценарий, но
финальная синхронизация может перевести пользователя на повтор iiko.

### 13.5. Синхронизация профиля

Изменение локального профиля завершится успешно, но задача выгрузки будет
переноситься и после исчерпания попыток станет ошибочной. Данные локальной базы и
iiko разойдутся.

### 13.6. SAGUR

При включённом регистрационном контуре событие не будет создано без успешного
результата iiko и `customer_id`. Восстановитель не сможет подтвердить неизвестные
результаты и после повторов переведёт записи в ручную обработку.

### 13.7. Диагностика

Локальная часть отчёта продолжит работать. Проверка `--live-iiko-readonly`
перестанет получать маркер.

### 13.8. Незатронутые функции

Главное меню, поддержка, купоны и другие сценарии без обращения к iiko продолжат
работать.

### 13.9. Временный кэш

Если процесс уже получил старый маркер и iiko продолжает его принимать, отдельные
вызовы могут работать до истечения установленного кодом 14-минутного кэша. После
перезапуска процесса отказ проявится немедленно.

## 14. Границы достоверности

### 14.1. Подтверждённые факты

- достижимые точки запуска существуют;
- один клиент подключён к трём ботам и двум фоновым процессам;
- используется адрес iiko Cloud API;
- используется `/api/1/access_token`;
- тело содержит `apiLogin`;
- значение берётся из `IIKO_API_KEY`;
- перечисленные рабочие методы находятся на `/api/1`;
- диагностический скрипт дублирует старую авторизацию;
- официальная спецификация содержит новый метод версии 2.

### 14.2. Обоснованные выводы

- если существующая интеграция когда-либо успешно работала, переданное значение
  `IIKO_API_KEY` было приемлемым для поля `apiLogin`;
- это не доказывает, что тот же секрет является новым `apiKey`;
- после отключения старого метода будут затронуты все вызовы единого шлюза.

### 14.3. Не подтверждено без рабочего окружения

- существует ли серверный `.env`;
- заполнены ли `IIKO_API_KEY` и `IIKO_ORG_ID`;
- какое значение фактически находится в старой переменной;
- какой `IIKO_BASE_URL` действует на сервере;
- какие сервисы запущены;
- какой коммит развёрнут;
- выполнялись ли реальные запросы iiko недавно;
- доступны ли ключу нужные организации и группы методов;
- есть ли действующее тестовое окружение iiko.

### 14.4. Противоречия и несоответствия

- имя `IIKO_API_KEY` предполагает новый ключ API, но код использует его как
  `apiLogin`;
- документация описывает включение через `IIKO_API_KEY`, но не объясняет его старую
  семантику;
- документация называет ветку разработки, но не фиксирует развёрнутый производственный
  коммит;
- `PROFILE_SYNC_ENABLED` по умолчанию включён, но без iiko-конфигурации обработчик
  остаётся ожидающим процессом без обработки задач.

## 15. Что необходимо безопасно проверить на сервере

Требуется отдельное разрешение на подключение к рабочему серверу. После его получения
нужно выполнить только безопасные проверки без вывода значений секретов:

1. Зафиксировать текущий развёрнутый коммит и ветку.
2. Получить состояние пяти затронутых контейнеров.
3. Проверить наличие и заполненность старых `IIKO_*` без вывода значений.
4. Классифицировать действующий `IIKO_BASE_URL` как стандартный или нестандартный.
5. Проверить журналы на факты недавних запросов и коды `IIKO-*`.
6. Подтвердить, что рабочий ключ действительно использует нужную организацию.
7. Не выполнять изменяющие запросы iiko.
8. Не копировать секреты в отчёт или командный вывод.

## 16. Решение по способу переключения

### 16.1. Принятое решение

Принята временная двухрежимная схема. Переходная версия приложения содержит два
механизма получения маркера:

- `v1` — действующий `POST /api/1/access_token` с `apiLogin`;
- `v2` — новый `POST /api/v2/access_token` с `appId`, `clientSecret` и `apiKey`.

Это не параллельное выполнение двух запросов. Каждый процесс при запуске выбирает
ровно один механизм и использует его до следующего перезапуска. Все рабочие методы
лояльности в обоих режимах продолжают обращаться к `/api/1`.

### 16.2. Контракт переключателя

1. Переменная `IIKO_AUTH_VERSION` имеет значение `v1` по умолчанию; `v2` включается
   только явно.
2. `is_iiko_configured` проверяет набор параметров выбранной версии так же, как
   сейчас проверяет `IIKO_API_KEY` и `IIKO_ORG_ID`.
3. При неполном или неизвестном наборе шлюз не создаётся, а приложение продолжает
   запуск без интеграции iiko — текущее поведение сохраняется.
4. `v1` использует только старый `IIKO_API_KEY` в значении `apiLogin`.
5. `v2` использует только `IIKO_APP_ID`, `IIKO_CLIENT_SECRET` и
   `IIKO_CLOUD_API_KEY`.
6. Изменение переменной вступает в силу после контролируемого перезапуска процесса.
7. Все пять сервисов должны быть приведены к одному режиму; краткий смешанный режим
   допустим только во время контролируемого поочерёдного перезапуска.
8. При ошибке обращения к iiko в режиме `v2` автоматический запрос через `v1`
   запрещён. Возврат выполняется
   оператором через `IIKO_AUTH_VERSION=v1`.

### 16.3. Последовательность перехода

1. Реализовать и протестировать оба метода и простой выбор версии.
2. Развернуть переходную версию с `IIKO_AUTH_VERSION=v1`.
3. Доказать отсутствие регрессий старого режима в новой версии кода.
4. Загрузить новые секреты в защищённое окружение.
5. Проверить `v2` в тестовом окружении и отдельной диагностической командой.
6. Установить `IIKO_AUTH_VERSION=v2` и контролируемо перезапустить пять сервисов.
7. Провести прикладные проверки и наблюдение.
8. При критериях отката вернуть `v1` вручную и перезапустить затронутые сервисы.
9. После согласованного периода стабильности удалить `v1` отдельным коммитом.

Переключение рабочего окружения не требует отдельного коммита, если переменные
окружения хранятся вне Git. Оно должно быть оформлено как отдельная эксплуатационная
операция с зафиксированными временем, исполнителем и результатом. Если описание
окружения версионируется отдельно, изменение версии авторизации фиксируется там без
секретных значений.

### 16.4. Причины и ограничения решения

Схема позволяет сначала доставить код без изменения поведения продукции, проверить
новый механизм отдельно и быстро выполнить управляемый возврат без развёртывания
другого образа.

Цена решения:

- временно хранятся оба набора секретов;
- увеличивается тестовая матрица;
- появляется риск забыть удалить старый путь;
- возврат на `v1` работает только пока iiko обслуживает старую точку.

Поэтому до начала реализации необходимо определить критерии завершения наблюдения и
крайний срок удаления `v1`. Старый механизм не является долговременным резервным
каналом.

## 17. Проектирование новой конфигурации

Переходная схема:

```text
IIKO_AUTH_VERSION=v1
IIKO_API_KEY=
IIKO_APP_ID=
IIKO_CLIENT_SECRET=
IIKO_CLOUD_API_KEY=
IIKO_ORG_ID=
IIKO_AUTH_URL=https://api-ru.iiko.services/api/v2/access_token
IIKO_BASE_URL=https://api-ru.iiko.services/api/1
IIKO_HTTP_TIMEOUT_SECONDS=10
```

`IIKO_API_KEY` в этой схеме является только старым `apiLogin` и допускается только
для режима `v1`. `IIKO_CLOUD_API_KEY` является новым ключом версии 2. Сходство имён
не означает взаимозаменяемость значений.

`IIKO_CLOUD_API_KEY` намеренно предлагается вместо `IIKO_API_KEY`: старое имя уже
используется для другого типа секрета и создаёт риск незаметной подмены.

Правила миграции:

1. Не считать старый `IIKO_API_KEY` новым ключом.
2. Классифицировать старое значение как `apiLogin` по текущей цепочке кода.
3. Сохранять его в защищённом окружении только на время переходного режима.
4. Не передавать старый секрет новому приложению.
5. Создать новый `IIKO_CLOUD_API_KEY` отдельно.
6. В режиме `v1` считать iiko настроенной только при наличии `IIKO_API_KEY` и
   `IIKO_ORG_ID`.
7. В режиме `v2` считать iiko настроенной только при наличии `IIKO_APP_ID`,
   `IIKO_CLIENT_SECRET`, `IIKO_CLOUD_API_KEY`, `IIKO_ORG_ID` и непустого
   `IIKO_AUTH_URL`.
8. При неполном наборе выбранной версии возвращать
   `is_iiko_configured == False`; шлюз не создаётся, запуск приложения не
   прерывается.
9. Параметры невыбранной версии не участвуют в проверке и не читаются механизмом
   авторизации.
10. После стабилизации удалить `IIKO_API_KEY`, поддержку `v1` и
    `IIKO_AUTH_VERSION`.

Новые секреты хранятся в окружении так же, как существующий `IIKO_API_KEY`, и не
должны выводиться в журналы. Введение отдельной подсистемы проверки или хранения
секретов в рамках этой задачи не требуется.

Окончательная схема после удаления `v1` содержит только новые реквизиты,
`IIKO_ORG_ID`, `IIKO_AUTH_URL`, `IIKO_BASE_URL` и тайм-аут. Временный переключатель
в ней отсутствует.

## 18. Проектирование двух методов авторизации

### 18.1. Минимальное изменение клиента

В существующем `IikoLoyaltyGateway` достаточно иметь:

- общий `_get_access_token`, выбирающий версию;
- старый метод получения маркера `v1` без изменения его запроса;
- новый метод получения маркера `v2`;
- общий существующий кэш `_AccessTokenState` на 14 минут.

Выделение отдельной подсистемы стратегий, разбор JWT, блокировки конкурентного
обновления, новая система повторов и изменение обработки рабочих запросов в объём
этой задачи не входят.

### 18.2. Адреса

- `v1` продолжает использовать `{IIKO_BASE_URL}/access_token`;
- `v2` использует полный `IIKO_AUTH_URL` со значением
  `https://api-ru.iiko.services/api/v2/access_token`;
- баланс, карты, клиенты и программы в обоих режимах продолжают использовать
  `IIKO_BASE_URL=https://api-ru.iiko.services/api/1`.

Полный адрес авторизации `v2` нельзя собирать присоединением к `IIKO_BASE_URL`.

### 18.3. Запрос версии 2

```json
{
  "appId": "...",
  "clientSecret": "...",
  "apiKey": "..."
}
```

Из ответа используется поле `token`. Полученный маркер помещается в существующий
14-минутный кэш — это меньше официального срока действия нового JWT и не требует
новой логики срока жизни.

### 18.4. Сохранение текущего поведения

- существующая обработка HTTP-ошибок не меняется;
- новые автоматические повторы не добавляются;
- автоматического возврата с `v2` на `v1` нет;
- секреты и маркер не добавляются в журналы;
- рабочие методы и их отображение ответов не меняются.

## 19. Дорожная карта реализации

### Этап 1. Получение реквизитов

- Цель: получить независимые новые реквизиты.
- Изменения: зарегистрировать приложение, получить `appId` и `clientSecret`, создать
  `apiKey`.
- Компоненты: портал разработчика, iikoWeb, защищённое хранилище секретов.
- Зависимости: административный доступ.
- Риски: потеря однократно показанного секрета, неверная организация, недостаточные
  права.
- Проверка: получение JWT в безопасном окружении.
- Критерий завершения: реквизиты сохранены вне репозитория и классифицированы.
- Откат: не требуется, старое приложение не затронуто.
- Сложность: низкая технически, административная длительность неизвестна.

Необходимые группы методов для текущего проекта по официальной спецификации:

- `Guests: info`;
- `Guests: creating`;
- `Guests: changing`;
- `Loyalty: dictionaries`.

### Этап 2. Настройки и переключатель

- Цель: добавить выбор версии, не меняя существующий порядок запуска приложений.
- Изменения: добавить `IIKO_AUTH_VERSION` со значением `v1` по умолчанию, новые
  реквизиты и расширить существующее свойство `is_iiko_configured`.
- Файлы: `settings.py`, `.env.example`, тесты настроек.
- Зависимости: утверждённые имена переменных.
- Риски: смешение старого и нового ключей с похожими именами.
- Проверка: значение по умолчанию, полные и неполные наборы `v1` и `v2`.
- Критерий завершения: при полном выбранном наборе шлюз создаётся; при неполном
  возвращается `None`, а запуск приложения продолжается.
- Откат: удалить ещё не развёрнутые изменения.
- Сложность: низкая.

### Этап 3. Два метода получения маркера

- Цель: сохранить старый запрос и добавить новый запрос авторизации в существующий
  клиент.
- Изменения: разделить текущий `_get_access_token` на методы `v1` и `v2`, а общий
  метод направляет вызов по `IIKO_AUTH_VERSION`.
- Файлы: `iiko_client.py`.
- Зависимости: этап настроек.
- Риски: неверный адрес или тело запроса `v2`.
- Проверка: точные адреса и тела обоих запросов; отсутствие автоматического
  переключения.

- Зависимости: обновлённые настройки и клиент.

- Сложность: низкая или средняя.

### Этап 6. Совместимый выпуск с активным режимом v1

- Цель: доставить двухрежимный код без изменения способа рабочей авторизации.
- Изменения: добавить в защищённое окружение `IIKO_AUTH_VERSION=v1`, развернуть новый

- Компоненты: Telegram, VK, MAX, синхронизация профилей, события SAGUR.

- Критерий завершения: новая версия кода работает в продукции с `v1` не хуже
  предыдущей версии.
- Откат: предыдущий образ и прежнее окружение.
- Сложность: средняя; первое окно развёртывания.

### Этап 7. Рабочее переключение на v2 и наблюдение

- Цель: включить новую авторизацию независимо от поставки кода.
- Изменения: заранее загрузить полный новый набор секретов, выполнить безопасную
  диагностическую проверку, установить `IIKO_AUTH_VERSION=v2`, поочерёдно
  перезапустить пять сервисов.
- Зависимости: успешный этап 8, подтверждённые права ключа, план наблюдения и
  проверенная инструкция ручного возврата.
- Риски: неверные права, организация, частичное переключение или устойчивые 401.
- Проверка: получение JWT, баланс, карта, регистрация трёх платформ, профильная
  очередь, SAGUR и показатели ошибок.
- Критерий завершения: все процессы работают в `v2`, прикладные сценарии успешны,
  критерии отката не достигнуты в течение согласованного периода.
- Откат: установить `IIKO_AUTH_VERSION=v1` и контролируемо перезапустить уже
  переключённые процессы; предыдущий образ является вторым уровнем отката.
- Сложность: средняя; отдельное окно переключения и период наблюдения.

### Этап 8. Удаление v1 отдельным изменением

- Цель: завершить миграцию и исключить бессрочное сохранение старого механизма.
- Изменения: удалить стратегию `v1`, `IIKO_AUTH_VERSION`, `IIKO_API_KEY`, старый

- Зависимости: документально завершённый период наблюдения и отдельное решение об
  отключении возможности возврата.
- Риски: преждевременное удаление последнего рабочего пути отката.
- Проверка: поиск `apiLogin`, `/api/1/access_token`, `IIKO_API_KEY` и
  `IIKO_AUTH_VERSION`; полный набор тестов.
- Критерий завершения: старый путь отсутствует в коде, окружении и эксплуатационных
  инструкциях.
- Откат: вернуть переходную версию только если старая точка ещё обслуживается;
  иначе исправлять `v2`.
- Сложность: средняя; отдельный коммит после стабилизации.

## 20. Обязательные тесты

1. Без `IIKO_AUTH_VERSION` выбирается `v1`.
2. Для полного набора `v1` свойство `is_iiko_configured` возвращает истину.
3. Для неполного набора `v1` свойство возвращает ложь без исключения.
4. Для полного набора `v2` свойство возвращает истину.
5. Для неполного набора `v2` свойство возвращает ложь без исключения.
6. При ложном `is_iiko_configured` все существующие функции сборки возвращают `None`.
7. `v1` использует `/api/1/access_token` и тело `{"apiLogin": ...}`.
8. `v2` использует `/api/v2/access_token` и тело с `appId`, `clientSecret`,
   `apiKey`.
9. Обе версии извлекают непустой `token` и используют существующий 14-минутный кэш.
10. В режиме `v1` не вызывается `v2`, а при ошибке `v2` не вызывается `v1`.
11. Рабочие методы в обоих режимах продолжают использовать `/api/1`.
12. Новые параметры передаются во все пять точек сборки клиента.
13. Диагностический скрипт умеет явно выбрать проверяемую версию.
14. Существующие тесты баланса, карт, регистрации и фоновых процессов продолжают
    проходить.
15. Отдельная интеграционная проверка `v2` выполняется только после получения
    реквизитов и разрешения на безопасный запрос.

## 21. Последовательность развёртывания

### 21.1. Подготовка

1. Зарегистрировать приложение.
2. Получить и защищённо сохранить `appId` и `clientSecret`.
3. Создать новый `apiKey` в iikoWeb.
4. Определить доступные ключу организации.
5. Проверить четыре необходимые группы методов.
6. Определить длительность и критерии периода наблюдения, крайний срок удаления
   `v1`, ответственных за переключение и возврат.
7. Сохранить резервную копию рабочего окружения без вывода секретов в журнал.
8. Зафиксировать текущий образ, коммит и результаты исходной прикладной проверки.

### 21.2. Первый выпуск: два режима, активен v1

1. Добавить в рабочее защищённое окружение `IIKO_AUTH_VERSION=v1`.
2. Развернуть переходный образ с обеими стратегиями.
3. Контролируемо перезапустить пять затронутых сервисов.
4. Подтвердить по безопасной диагностике, что каждый сервис выбрал `v1`.
5. Убедиться, что `/api/v2/access_token` рабочими сервисами не вызывается.
6. Проверить регистрацию, баланс, существующую карту, профильную очередь и SAGUR.
7. При общей регрессии вернуть предыдущий образ; до её устранения к `v2` не
   переходить.

Этот выпуск может состоять из нескольких технических коммитов, но с точки зрения
эксплуатации он является одним совместимым выпуском без смены способа авторизации.

### 21.3. Проверка v2 без переключения рабочих сервисов

1. Добавить новые секреты в тестовое окружение.
2. Получить JWT через `v2`.
3. Выполнить безопасный `customer/info`.
4. Проверить баланс и существующую карту.
5. В тестовой организации проверить изменяющие сценарии.
6. Загрузить полный новый набор в рабочее защищённое окружение, не меняя
   `IIKO_AUTH_VERSION=v1`.
7. Запустить отдельную разрешённую диагностическую проверку с явным `v2`.
8. Не продолжать при неподтверждённых правах, организации или безопасности
   диагностического запроса.

### 21.4. Эксплуатационное переключение на v2

1. Зафиксировать начало окна и исходные показатели ошибок.
2. Изменить только `IIKO_AUTH_VERSION` с `v1` на `v2`.
3. По утверждённому порядку перезапустить сервисы; после каждого перезапуска
   подтвердить выбранный режим и состояние процесса.
4. Не допускать длительной работы пяти сервисов в разных режимах.
5. Проверить получение JWT, баланс и существующую карту.
6. Проверить регистрацию в Telegram, VK и MAX.
7. Проверить профильную очередь и восстановление SAGUR.
8. Контролировать ошибки авторизации и затронутые прикладные сценарии.
9. Зафиксировать окончание переключения, версии всех сервисов и результаты проверок.

Это переключение является операцией с окружением, а не обязательным коммитом в
репозитории приложения. Значения секретов в Git не добавляются.

### 21.5. Наблюдение и очистка

1. В течение согласованного периода контролировать прикладные ошибки и обновление
   JWT.
2. Не считать само отсутствие 401 достаточным доказательством: должны проходить все
   затронутые бизнес-сценарии и фоновые процессы.
3. После выполнения критериев стабильности отдельно одобрить отказ от возврата на
   `v1`.
4. Удалить `v1` и переходный переключатель отдельным коммитом и выпуском.
5. Удалить старый `apiLogin` из защищённого окружения.
6. Повторно проверить отсутствие старых имён, адреса и вызовов.

## 22. Откат

### 22.1. Условия начала

- массовые 400 или 401;
- ключ не видит нужные организации;
- недоступны баланс или карты;
- регистрация блокируется на всех платформах;
- растёт число ошибочных задач фоновых очередей;
- новая авторизация устойчиво возвращает ошибку.

### 22.2. Порядок

1. Остановить дальнейшее развёртывание.
2. Подтвердить, что старая точка `/api/1/access_token` ещё доступна и старый
   `apiLogin` не удалён.
3. Установить `IIKO_AUTH_VERSION=v1` в защищённом окружении.
4. Контролируемо перезапустить уже переключённые процессы, а затем привести все пять
   сервисов к одному режиму `v1`.
5. Убедиться по безопасному стартовому сообщению, что процессы действительно выбрали
   `v1`.
6. Проверить регистрацию, баланс, карту и фоновые очереди.
7. Зафиксировать причину, HTTP-статусы, время и список возвращённых
   сервисов.
8. Если проблема вызвана общей регрессией переходного образа, а не только `v2`,
   вернуть предыдущий образ и прежнее окружение.

После официального отключения старой точки возврат предыдущего образа не восстановит
интеграцию. Автоматический возврат отдельного запроса с `v2` на `v1` не является
допустимым способом отката.

### 22.3. Компрометация `clientSecret`

1. Перевыпустить секрет в портале разработчика.
2. Учесть немедленный отзыв прежнего секрета.
3. Обновить защищённое окружение.
4. Перезапустить пять затронутых процессов.
5. Проверить получение нового JWT.
6. Не передавать секрет или JWT технической поддержке.

Для поддержки подготовить:

- точное время и часовой пояс;
- имя сервиса;
- безопасный путь запроса;
- HTTP-статус;
- код ошибки;
- идентификатор организации при допустимости его передачи;
- версию приложения и коммит;
- число повторов;
- факт перевыпуска секрета.

## 23. Критерии готовности

### 23.1. Готовность совместимого выпуска

- оба метода получения маркера реализованы в существующем клиенте;
- без `IIKO_AUTH_VERSION` сохраняется режим `v1`;
- неполный набор выбранной версии приводит к `is_iiko_configured == False`, но не
  останавливает приложение;
- автоматический переход между версиями невозможен;
- тесты `v1` подтверждают отсутствие регрессий;
- переходный образ развёрнут с `IIKO_AUTH_VERSION=v1`;
- все пять сервисов подтверждают режим `v1`;
- рабочие сценарии проходят, а `/api/v2/access_token` не вызывается рабочими
  сервисами.

Выполнение этих условий означает только готовность к отдельной проверке и включению
`v2`, но не завершение миграции.

### 23.2. Готовность и успешность переключения на v2

- новые реквизиты полны и хранятся вне репозитория;
- права ключа и организация подтверждены;
- тестовая и отдельная диагностическая проверки `v2` успешны;
- ручная процедура возврата на `v1` подготовлена и проверена без раскрытия секретов;
- все пять сервисов после перезапуска подтверждают режим `v2`;
- JWT получается через `/api/v2/access_token` с тремя новыми реквизитами;
- старый `IIKO_API_KEY` не читается стратегией `v2`;
- автоматических обращений к `/api/1/access_token` после переключения нет;
- рабочие методы остаются на `/api/1`;
- полученный маркер использует существующий 14-минутный кэш;
- секреты отсутствуют в коде, тестах, журналах и сообщениях;
- проверены Telegram, VK, MAX, очередь профилей и восстановление SAGUR;
- критерии отката не достигнуты в течение согласованного периода наблюдения.

На этой точке `v2` считается введённой в эксплуатацию, но `v1` ещё временно остаётся
в коде и окружении как управляемый путь возврата.

### 23.3. Завершение миграции

Миграция считается полностью завершённой только после отдельного решения об очистке:

- период наблюдения документально завершён;
- стратегия `v1` и вызов `/api/1/access_token` удалены из исполняемого кода;
- `apiLogin`, `IIKO_API_KEY` и `IIKO_AUTH_VERSION` удалены из настроек и окружения;
- старый секрет удалён из защищённого хранилища по принятой процедуре;
- переходные тесты и инструкции заменены окончательными;
- поиск по репозиторию не находит исполняемого старого пути;
- все автоматические и прикладные проверки `v2` проходят;
- документация соответствует окончательной однорежимной архитектуре.

- интеграционная проверка — отдельное безопасное окно;
- совместимый выпуск на `v1` — первое контролируемое окно;
- переключение на `v2` — второе контролируемое окно плюс период наблюдения;
- удаление `v1` — отдельное небольшое изменение после стабилизации.

Оценка не включает непредвиденные ограничения прав нового `apiKey`, отсутствие
тестовой организации или необходимость изменения способа хранения секретов.

## 26. Следующий шаг

Техническая реализация завершена. Зафиксированы:
