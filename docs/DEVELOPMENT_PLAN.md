# План разработки vtelemax (версия 1)

Документ фиксирует согласованный план разработки монорепозитория с единой строгой идентификацией пользователей по телефону.

## 1. Зафиксированные решения

1. Формат проекта: монорепозиторий.
2. Архитектура: `core` + `adapters` + `infrastructure` + `apps`.
3. Идентификация: strict identity (один телефон = один человек).
4. Общая бизнес-логика и тексты хранятся в ядре, а не в адаптерах.
5. Тестирование обязательно: unit, integration, adapter-contract.
6. Рабочая ветка разработки: `codex/develop-cai` (активная), `main` (стабильные точки).

## 2. Целевое дерево проекта

```text
src/vtelemax/
  core/               # доменные модели, use-cases, бизнес-правила
  adapters/           # telegram, vk, max (только транспорт)
  infrastructure/     # postgres, redis, внешние клиенты
  apps/               # точки входа каждого бота
tests/
  unit/               # быстрые тесты ядра
  integration/        # тесты репозиториев и БД
  adapter_contract/   # тесты контрактов адаптеров
docs/
  ARCHITECTURE.md
  DEVELOPMENT_WORKFLOW.md
  DEVELOPMENT_PLAN.md
```

## 3. Этапы разработки

### Этап 0. Инициализация (выполнено)

1. Инициализирован репозиторий и ветки.
2. Добавлен базовый каркас проекта.
3. Добавлены стартовые unit-тесты strict identity.
4. Оформлены базовые документы и скрипты окружения.

### Этап 1. Доменная модель и контракты (в работе)

Цель: закрепить неизменяемое ядро правил.

Текущий прогресс:

1. Выполнен подэтап 1.1: выделены доменные модели, порты и use-case регистрации в `core`.
2. Выполнен подэтап 1.2: зафиксирована SQLAlchemy/SQL схема strict identity для PostgreSQL.

1. Уточнить доменные сущности: `Person`, `Phone`, `PlatformAccount`.
2. Добавить интерфейсы репозиториев в `core` (портовый слой).
3. Описать use-case сценарии регистрации/поиска пользователя.
4. Зафиксировать ошибки домена и единый контракт ответов.

Критерий готовности:

1. Ядро не зависит от SDK Telegram/VK/MAX и от ORM.
2. Есть unit-тесты на позитивные и конфликтные сценарии.

### Этап 2. Инфраструктура идентификации (PostgreSQL)

Цель: перейти с in-memory на постоянное хранилище.

1. Создать схемы таблиц: `persons`, `phones`, `platform_accounts`.
2. Ввести уникальные ограничения для strict identity.
3. Реализовать SQLAlchemy-репозитории.
4. Подготовить миграции и интеграционные тесты репозиториев.

Критерий готовности:

1. Конфликтные привязки ловятся на уровне домена и БД.
2. Интеграционные тесты проходят локально через `pytest`.

### Этап 3. Единый сценарный слой (use-cases и меню)

Цель: вынести общие тексты/меню/переходы в ядро.

1. Описать модель меню и команд, общую для всех платформ.
2. Вынести тексты сообщений в единый модуль ресурсов.
3. Реализовать use-cases: старт, регистрация, профайл, тикет.
4. Добавить unit-тесты для сценариев и ветвлений.

Критерий готовности:

1. Поведение идентично для всех ботов при одинаковом вводе.
2. Дублирование бизнес-логики в адаптерах отсутствует.

### Этап 4. Адаптеры Telegram/VK/MAX

Цель: подключить ядро к каждому боту через единые контракты.

1. Telegram-адаптер (`aiogram`): маппинг update <-> core command.
2. VK-адаптер (`vkbottle`): маппинг event <-> core command.
3. MAX-адаптер: маппинг event <-> core command.
4. Adapter-contract тесты для унификации поведения.

Критерий готовности:

1. Один и тот же сценарий дает одинаковый результат на 3 платформах.
2. Адаптеры не содержат доменных правил.

### Этап 5. Нефункциональные требования и выпуск MVP

Цель: подготовить стабильный минимально полезный релиз.

1. Логирование, трассировка, обработка ошибок.
2. Конфигурация через `.env` и валидируемые settings.
3. Документация запуска/тестирования/архитектурных решений.
4. Smoke-проверка трех приложений в локальном контуре.

Критерий готовности:

1. Проект воспроизводимо поднимается по документации.
2. Все обязательные тесты проходят в CI/локально.

## 4. Контрольные точки (Milestones)

1. M0: Каркас репозитория и стартовые тесты (выполнено).
2. M1: Порты и use-cases ядра strict identity.
3. M2: PostgreSQL-репозитории и миграции.
4. M3: Единые тексты/меню и сценарии.
5. M4: Telegram/VK/MAX адаптеры на общем ядре.
6. M5: Стабильный MVP с документацией и тестами.

## 5. Definition of Done для каждой задачи

1. Код покрыт комментариями и docstring на русском языке.
2. Добавлены или обновлены тесты.
3. Обновлена документация при изменении поведения.
4. Коммит содержит одну логическую завершенную единицу.
5. Коммит-message на русском языке.

## 6. Шаблон шага разработки (повторяемый цикл)

1. Согласовать подзадачу.
2. Внести изменения в код.
3. Запустить релевантные тесты.
4. Обновить документацию.
5. Сделать логический коммит.
6. Перейти к следующему шагу.
